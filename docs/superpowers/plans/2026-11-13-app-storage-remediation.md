# 重点 APP 存储回收实现方案

**目标：** 把剩余大占用落实到可验证的资源回收，优先处理百度网盘、Swiftgram，并按待确认量推进红果短剧、TikTok、抖音、汽水音乐及抖音极速版。

**架构：** 继续使用现有清理引擎及单一规则表。普通缓存走现有 Sweep；由 APP 自身索引管理的资源优先走 APP 的资源清理机制。定位、可恢复性验证、自动启用分阶段交付，不把识别格式当作删除授权。

**2026-11-14 版本兼容修正：** 按用户要求，以实际资源契约与接口能力作为长期适配依据；不要求必须取得与用户同版本的 IPA 才开始工作，也不将所有生产规则永久绑定一个版本等号。下文“匹配构建”指核实适配器与实际实现兼容，可覆盖经证明兼容的多个版本；版本/构建仍记录并使升级前旧任务失效。具体规则与 Swiftgram 13.0/13.2 的源码对比见 [版本兼容与资源接口依据](../../app-rules/版本兼容与资源接口依据.md)。

**技术栈：** 当前 Theos / Logos、Foundation / UIKit、SDK 16.5、iOS 16–17、RootHide，保持包身份、架构、作者“目目”及逐版本中文更新日志。

**依据：** 原修复方案任务 10；当前源码基线 `3c5f5d89cd85f8ac6c62b690b96ffe0e17441e88`；两份用户主动导出的报告。用户统计、账号、资源名称及原始 JSON 只保留在本地 `packages/`，不随本方案发布。

**状态：** 本文是实现方案，不代表下面的 APP 专属清理已经实现或真机通过。0.7.2-97.1 已解决快速汇总；以下工作解决实际回收范围。

**2026-11-13 实施增量：** 用户要求方案后直接实现，已先落地有已有目录及文件命名证据的[抖音 ALog 日志规则](../../app-rules/com.ss.iphone.ugc.Aweme.md)。只回收匹配版本的具体日志文件，并增加真实退出门及回执说明；原生/构建与真机状态以对应提交的交付记录为准。任务 1 的 PDF 定位、百度下载副本和 Swiftgram 媒体桥接仍未完成，不以这条日志规则冒充整体适配。下表“规则为空”是方案基线事实。

## 1. 根因与工程决策

| 已核对事实 | 对应解决方式 |
|---|---|
| Scanner 已读取 APP 版本并传给 Sweep；生产 APP 规则表仍为空 | 复用现有版本链，注册经过验收的精确规则；不重复开发版本传递功能 |
| 必要状态规则把 WebKit 等父目录整片保留 | 将已验证网络缓存与登录/网站数据区分；不移除整个 WebKit 的保留规则 |
| Swiftgram 的共享根混有主库、索引和媒体 | 采用 APP 自身的媒体清理事务；不将 App Group 根加入通用删除范围 |
| 最大文件列表中硬链接只有属性，缺少格式识别；普通文件也不识别 PDF 头 | 对文件做有界格式识别，独立展示 PDF 候选，帮助定位离线文件 |
| 未知目录、资源名统一匿名化，开发侧无法把大占用与公开 SDK 目录对应 | 对已核实技术名称使用精确目录词典；账号、未知目录、文件名继续匿名化，并给出未知项计数 |
| 快速报告汇总旧记录，原快照时间不变 | 用已有单 APP / 单目录检测更新具体缺口，然后手动导出一次；不恢复全 APP 深度补采 |

## 2. 第一项交付：解决“找不到资源”的具体障碍

**文件：** `AxsCacheKeeperInspection.h/.m`、`AxsCacheKeeperDiagnostics.m`、`Scanner.m`、`Prefs/InspectionPage.m`、`tests/diagnostics_tests.m`，并在现有原生测试入口增加定向检查。

- [ ] 增加独立的“定位 PDF”模式，只遍历用户选中的一个目录，不附带主容器、App Group、安装包搜索根，不进入硬链接孪生搜索。不能只传空 `searchRoots`：当前初始化会回退到本目录，必须显式关闭孪生阶段。
- [ ] 该模式总预算取先到者：10000 个枚举项、16 MiB 格式样本、5 秒单调时钟；逐项及读取前后检查，每批最多 64 项。预算是协作式停止，单次系统 I/O 不能保证硬超时；UI 保持响应并可取消，不能把 5 秒写成绝对完成承诺。
- [ ] 返回 `inspectionMode=pdfLocate`、`enumeratedCount`、`sampleBytes`、`durationSeconds`、`stopReason`（finished/entryLimit/byteLimit/timeLimit/cancelled/error）、`coverageComplete`；预算耗尽返回已找到候选和“范围未扫完”，不自动扩根、重扫或继续排队。未命中且覆盖不全不能显示“没有 PDF”。
- [ ] 将普通文件和硬链接的只读格式探测共用同一安全读取函数：先执行现有敏感范围检查，再经已核验目录 fd 打开文件，`O_NOFOLLOW | O_NONBLOCK`，比较打开前后设备号、inode、大小、修改时间；最多读取现有 4096 字节样本，变化/读取失败显式计数，不跟随符号链接。硬链接不能绕过敏感范围检查读取文件头。
- [ ] 添加 `%PDF-` 头识别。PDF 只作为格式标签；不解析正文，不在报告写入文件头、摘要、URL 或内容哈希，不因此改变清理判断。
- [ ] 报告增加 `pdfCandidates`（按大小最多 10 个路径样本）、`pdfPathCount`、`pdfCandidatesTruncated`；路径数包含硬链接路径，不把数量或逻辑字节当物理占用。独立于“最大普通文件/最大硬链接”，避免被其他大文件挤掉。
- [ ] 面板显示“PDF 特征候选”，使用现有 Filza 定位入口；标注“候选，不代表就是测试文件或可以删除”。格式读取失败与未找到候选分开显示。
- [ ] 技术名称词典只加入有来源证据、路径层级和适用 APP 的精确项；拒绝“Library 下全部名称原样导出”“account 前缀后保留号码”等宽放行。未知技术名仍匿名化，本轮无法证明的目录不得进入删除规则。
- [ ] 新定向报告只保存在本次诊断会话内存，并入手动导出的同一份 JSON；确认离页释放。当前 `CKInspectRequests` 会写 `Status/*.inspection.plist`，不能直接复用该落盘链路。实现前先打通权限及调用方身份可核验的本机内存传递；没有这条链路时不开放新入口，不用临时报告自动落盘作替代。既有清理配置和运行回执与新诊断报告分别处理。
- [ ] 原生回归覆盖：普通 PDF、无后缀 PDF、同 inode 的两个硬链接、比其他大文件小的 PDF、同名非 PDF、读取失败、扫描中替换、符号链接、11 个候选截断；注入时钟和枚举器分别触发三种预算，断言不触及相邻搜索根、不进入孪生阶段、取消后不继续读取；导出不含原文，定向采集前后文件清单不新增报告。

**验收结果：** 对百度网盘的既有 Caches 范围做一次定向检测后，能给出 PDF 格式候选或明确的未覆盖/未识别结果；用户无需手动在 Filza 遍历整个容器。加密、压缩或并非 PDF 格式存储的内容可能无法命中，不能据“未命中”认定本地文件不存在。

本项为后续删除提供定位能力，不能单独算作 APP 清理适配完成。需要该项后继续执行任务 3、4、5；不能以“诊断做完”结束整个回收任务。

## 3. 百度网盘：按可恢复资源清本地副本，保留下载记录

**文件：** 新增专属 `AxsCacheKeeperBaiduAction.h/.m`；接入 `Cleaner.m`、`Scanner.m` 和既有回执展示；规则证据在 `docs/app-rules/com.baidu.netdisk.md`。新增文件是方案中的文件，当前尚不存在。

### 已选择的实现路线

1. 主路线为目标 APP 自身下载管理器的“移除本地副本”资源操作。先将测试文件与真实资源 ID、本地各副本、恢复来源和下载索引对应，再核实安装构建的真实方法及调用约定；不臆造 selector，也不调用删除云端文件或删除下载记录的动作。
2. 每个候选都须证明可重新获取、没有用户排除、不是上传中或唯一副本；同一资源的硬链接和索引由资源管理器保持一致。无法核对其全部受影响范围时不执行，不能绕过到路径 unlink。
3. 共用动作边界：排队时和真正调用前均复核 APP 开关、版本/构建、规则修订、进程实例、资源证据和 `excludedPaths`。任何成员失效都撤销未启动请求；资源 ID 只保存在内存，导出只含脱敏状态及计数。关闭配置不再发新动作，已进入不可取消 API 的操作不得伪报已取消。
4. 首次仅给匹配构建提供显式验证动作。请求绑定 bundle、版本、构建、规则修订、实例和 token；按真实 API 的线程约定调用，回调匹配原请求才更新该次回执。达到 15 秒无回调只标记等待超时，仍保留该实例的 in-flight 状态；晚回调或实例确实退出前，新 token 也不能并发进入同一资源动作。
5. 资源恢复、登录和下载列表三轮验收通过后再自动触发。目标 APP 从活跃转后台且尚有执行时间时最多启动一次；若用户划掉后台导致进程已退出，明确记录未执行，等待下次符合条件的生命周期，不由 SpringBoard 代删资源树。

### WebKit 网络缓存的受限备选

`removeDataOfTypes:modifiedSince:completionHandler:` 没有逐文件、逐资源或路径排除参数；`forDataRecords:` 也不提供任意路径排除。即使仅指定 `WKWebsiteDataTypeDiskCache`，仍不能据此证明不会影响某个待保留下载副本。

只有在匹配安装构建中核对了真实 data store 与缓存根，并能证明**该操作的整个作用范围**没有用户排除、唯一副本或恢复性未知资源时，才可评估仅 DiskCache 的动作。任一条件不满足就禁止调用，不能先整库清理再声称“跳过排除项”。当前证据不足，**本阶段不启用百度整 store 清理**；也不把默认 store 假定为全部 WebView 使用的 store。Cookies、LocalStorage、IndexedDB、网站离线数据仍不在清理范围。

### 下载 PDF 的完成条件

- 用一个可重新下载的测试文件做对照，记录明确候选与云端可恢复性；不能仅以“约 8.3 MB”认定身份。
- 清理后需要同时验证：所选资源在没有联网重新下载的情况下不再提供原来的离线读取、联网可重新获取并完整打开、登录保留、下载列表和其他文件操作正常。若 APP 仍保留独立副本，继续核对下载管理链路，不扩大 WebKit 范围去凑删除效果。
- 云端已删、无权限、未上传完成或唯一副本不进入“可恢复下载副本”规则。
- API 回调只证明该次 API 完成；回执分别记录请求、回调、测试结果与逻辑统计，不编造实际释放字节。

**原生/设备测试：** 资源 ID 与恢复证据不匹配不执行；用户排除和唯一副本完全不变；排队后配置/规则变化不调用；不同 bundle/版本/构建不执行；重复 token 不重复执行；15 秒超时后另一个 token 也被 in-flight 拦截，晚回调只归原请求；整 store 条件不全时 API 调用次数为零。三轮“使用—清理—重开—恢复下载”以真机结果为准。

## 4. Swiftgram：使用媒体资源清理机制，保留主库与索引

**文件：** 专属 `AxsCacheKeeperSwiftgramAction.h/.m`（实际桥接形式在匹配安装构建后确定，不预设 Swift 可直接用 Objective-C selector 调用）；`Cleaner.m` 的目标进程动作入口；`docs/app-rules/app.swiftgram.ios.md`。

- [ ] 对齐安装包版本、构建号与对应源码/符号。公开主线代码只能证明路线存在，不能当成已安装版本的 ABI 证据。
- [ ] 追踪现有 Storage Usage 页面调用的 `context.engine.resources.clearStorage` 到资源事务，核实选择的媒体分类及需要保留的资源；不能直接调用包含额外副作用的“清空全部”UI 动作。
- [ ] 桥接必须在 APP 进程内使用真实资源上下文及有效账号实例，显式排除本地未发送、上传中、不可恢复或无法分类资源。不得伪造账号对象或按路径通配 `_partial`。
- [ ] 同样遵守任务 3 的配置/排除/实例/规则复核及 in-flight 约束；如果 APP 的资源接口不能表达应保留集合，就不能调用更宽范围的清理操作。
- [ ] 优先复用应用已有存储期限/容量管理能力；只有能观测和核验的接口才自动接入。若该安装构建无法安全桥接，记录具体缺失的符号/上下文和下一步验证项，不退化成对共享目录直接 unlink。
- [ ] 保留 `postbox/db/db_sqlite`、WAL/SHM、账号元数据、消息/资源索引；清理容量只统计选中的媒体资源，不把数据库大小纳入预期释放量。
- [ ] 验收普通云端照片/视频/文档清理后可重取，消息与检索完整，草稿和上传不丢失，另一个账号及扩展正常；资源进度、结束和失败由实际回调记录。三轮通过后才启用自动策略。

**关键限制：** 目前没有把公开主线与安装构建完成映射，也没有验证可用的运行时桥接。该项有明确实现路线，但尚不能宣称“现成接口已经能直接 hook”。

## 5. 红果短剧、TikTok、抖音系：逐个目录进入同一规则表

**文件：** `AxsCacheKeeperCleanupRules.h/.m`、必要的 APP 专属读取实现、原生夹具、`docs/app-rules/<bundle>.md`。继续使用已有 `decisionForBundle:version:relativePath:state:evidence:`，不建立远端规则平台或第二套删除引擎。

本组顺序：红果短剧 → TikTok → 抖音 → 汽水音乐 → 抖音极速版；各 APP 独立验收，不让一个 APP 的通过结果放行其他 APP。

- [ ] 对单个 APP 的最大三个待确认范围定位技术身份；优先处理有公开 SDK 用途或实际运行证据的封面、可重取媒体片段、可再生资源。名称、年龄、文件类型和“没有发现数据库”均不能单独授权删除。
- [ ] 每条生产规则精确绑定 bundle、相对资源路径、规则修订、保留范围、恢复所需索引和依赖快照，并声明实际兼容契约。记录 APP 版本/构建用于回归和已知不兼容排除；稳定资源契约在更新后通过核验即可继续，不无条件停用。私有接口桥接则必须核实实际调用约定和语义；未知实现不能仅凭同名方法放行。现有版本传递及升级取消旧 job 的链路保留。
- [ ] 草稿、编辑项目、上传、离线下载及业务数据库保持原有保留优先级。TikTok 与国内抖音分别注册，不能按厂商或路径相似共用删除授权。
- [ ] 已验证资源目录只有在其依赖完整核验后才返回 Delete；新版本先重新验证，只有兼容契约失配的专属范围撤销删除授权，不影响标准缓存和独立兼容范围。拒绝把整个 Library 或 Application Support 当可清根。
- [ ] 无法根据现有资料确认用途的范围进入“具体证据缺口”清单，写明缺少的是目录身份、恢复来源、索引依赖还是版本对应。每个迭代至少应交付一个真实可回收范围及保留结果，不能只重复输出“未知”。

**回归：** 版本/构建不匹配、规则升级中止旧 job、草稿/唯一副本不变、依赖被改后停止、可恢复范围确实删除、删除失败不记成功、第二轮新增仍回收；设备验收覆盖清理前后同口径容量和恢复播放/打开。

## 6. 交付与停止条件

执行次序固定为：有界定位与内存传递 → 百度测试资源的实际回收闭环 → Swiftgram 媒体事务 → 红果、TikTok、抖音、汽水、抖音极速版逐个范围。目标构建的方法/上下文核对由开发侧完成；不再让用户反复全量采集或手动遍历 Filza。具体接口无法核实时，在对应 APP 条目列出缺失的方法、构建映射或资源语义，不凭猜测发布自动删除。

- 日常“采集诊断”继续保持快速、只读、固定 APP 总数；报告仅内存，手动导出才创建分享文件，不自动上传。
- 不恢复 126 APP 全量深度队列。证据更新使用现有单 APP/单目录入口；第一轮只处理上述明确范围，遇到截断记录缺口，不自动追加到整个设备。
- 每个产品改动：先备份 → 有效失败回归 → 实现 → 独立审查 → 普通提交推送 → Actions 原生和 RootHide 编译 → deb/作者/更新日志核验 → 提供真机步骤。
- 原生入口为 `python3 tests/run_native_tests.py`，新增夹具接入同一入口；预期退出 0 且所有断言通过。Windows 返回 UNAVAILABLE/退出 2 不计通过；真实原生及 Theos/deb 验证由该提交的 `.github/workflows/build.yml` 完成，不能以文档检查替代。
- “源码通过”“包已发布”“设备动作已完成”“资源可恢复”分别记录。只有删除与恢复都通过，才把对应 APP 范围标记为已适配。
- 本方案没有承诺清除 APP 安装包、聊天主库、照片库或全部系统显示的占用，也不承诺单次网络缓存清理必然移除独立下载副本。

### 功能包交付后的真机验收

以下是后续对应功能包的验收步骤，不表示 0.7.2-97.1 已具备新清理动作。每次只验证一个 APP；使用明确可恢复的测试资源，不用唯一副本试删。

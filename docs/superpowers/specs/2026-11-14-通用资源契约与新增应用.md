# 通用资源契约与新增应用

## 用户目标

本轮 SSH 只调查当前设备，取得的依据用于插件内置能力。新装 APP 应直接进入自动发现流程，复用 iOS、Foundation 及已验证 SDK 的存储契约；不以逐 APP 收集目录、每个版本添加名单或要求用户再次 SSH 为日常使用前提。已开启的应用清理可丢弃缓存和非必要资源，并在资源所有者提供合适接口时限制再次落盘。

## 实现选择

沿用现有 Theos、iOS 16–17、RootHide、插件身份与配置。继续使用已有清理规则、Sweep、Job、回执和网络缓存控制模块，不另建远程规则服务或第二套清理引擎。

1. 共享安装提供器从系统取得应用与容器身份。缓存只放内存：未变项校验少量元数据，新增或变化项才重新解析安装信息。版本号用于说明样本；构建、安装包、Info 与主程序的真实身份用于撤销过期作业。
2. 通用清理按资源用途契约判断。现有 `Library/Caches`、`tmp` 平台规则对未来新 APP 同样适用；用户排除、必要保留、身份核验与进程条件继续优先。未知文件不因扩展名、年龄或未识别出数据库就获得删除授权。
3. 通用产生限制在 APP 进程内使用资源所有者 API。Foundation `NSURLCache` 的磁盘容量策略不依赖 APP 名单；创建时及后续设置均受策略约束，关闭后恢复 APP 最新请求。该能力不代表 WebKit、自建数据库或任意 SDK 都已受控。
4. SDK 或私有媒体资源按同一契约接入：检测实际能力、核实签名与对象上下文、确定可恢复集合及必要保留、执行前再次检查、按真实结果记回执。一个已支持契约可以覆盖多个 APP 与多个版本；新私有存储协议不能凭编译信息推断语义，也不能承诺永远无需扩展插件能力。
5. 诊断汇总安装与配置并集，标明能力/记录来源及未知状态。自动发现不会替用户开启未配置应用，也不会绕过已有排除。失败只影响对应能力或范围，不能填假零值或伪报全部适配。

## 证据及验证

当前设备的 296 个安装条目、400 个独立容器及 132 个可管理 APP 已完成有界基础核查；完整清单只保留本地。该结果提供当前结构样本，不是所有资源可删的证明。

回归须证明：新 APP 不需要名单就能进入提供器；同短版本更换 build/程序会停止旧清理；身份未变的对照能真实清理；缺失/损坏身份不能继续；未变项不反复解析；新缓存构造器收到零磁盘容量且内存容量不变；关闭策略恢复请求；诊断不写配置或自动报告文件。

原生回归、UIKit、Theos/deb 与真机分别记录。安装新包、执行资源操作和恢复验收须在具体包及步骤可供核对后按设备授权进行。PDF 内存定位、百度下载资源和 Swiftgram 媒体事务仍按原方案推进，不把这份设计或安装清单当成已实现结果。

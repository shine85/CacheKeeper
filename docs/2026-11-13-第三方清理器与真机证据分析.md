# 四个清理仓库与真机证据分析

核查日期：2026-11-13。固定提交源码通过 GitHub API 读取；没有运行第三方清理器，也没有将其删除代码或权限配置导入 CacheKeeper。以下是源码分析，不是四个产品的真机兼容认证。

## 结论

最值得借鉴的是 Caz 的分阶段目录报告、硬链接去重统计、具体 APP 的例外表，以及 TrollCleaner 对“路径不存在 / 无权读取 / 内容为空”的区分。应独立实现符合 CacheKeeper 的采集和回执链路。没有一个仓库能直接证明百度网盘 PDF 或 Swiftgram 所有媒体可安全回收；更不能用整树删除替代 APP 版本和恢复证据。

## clearnbox：与我们相似的保留策略，不能作为 WebKit 解锁依据

源码：[CBCleanManager.m](https://github.com/o2ol/clearnbox/blob/c50bc0153409717aad211856554a7eed5860fdd6/CBCleanManager.m)、[CBStorageInfo.m](https://github.com/o2ol/clearnbox/blob/c50bc0153409717aad211856554a7eed5860fdd6/CBStorageInfo.m)、[entitlements.plist](https://github.com/o2ol/clearnbox/blob/c50bc0153409717aad211856554a7eed5860fdd6/entitlements.plist)。

- `fillGroups:fromProxy:`（约 155 行）从 `groupContainerURLs` 取组目录，和 CacheKeeper 已有发现链路相近。CacheKeeper 还要保持系统重新解析容器、范围校验与共享目录只读边界。
- `isLoginRiskName:`（约 297 行）按 WebKit、account、login、session、token 等名称保留；`deleteContentsOfDirectory:`（约 371 行）清 Caches 时跳过这些直接子项。这与百度截图里的 WebKit/nsurlsessiond 保留原因方向相同，照搬不会解决残留。
- `scanCategoriesForApp:` 将 Caches、tmp、日志、网页数据、启动快照、组缓存分别呈现。按用途展示可参考，但组缓存不是天然可删，仍可能有扩展和其他进程在使用。
- `directorySize:maxFiles:skipLoginRisk:` 按 `NSURLFileSizeKey` 汇总，跳过隐藏文件，部分调用有 8000 项上限；错误处理返回 YES，截断并非完整覆盖证明。未看到该扫描实现按 inode 去重，不能把逻辑体积直接当可释放物理空间。
- `deleteContentsOfDirectory:` 的单文件分支先算大小，删除结果不决定返回大小；目录内单项失败不完整上报。CacheKeeper 不采用这套释放量口径。
- `CBStorageInfo` 使用 volume capacity API；其中“重要用途可用容量”与普通空闲容量分属不同口径。若未来展示设备容量，应分开标明，不能把两者差值归因于插件。
- `CBCleanManager.m:594–600` 的异常钳制不是“截到容器占用 5 倍”：在容器占用大于 1 MiB 且可清量超过 5 倍时，它把值改为容器占用本身，随后才在 `:602–605` 重测；这只能借鉴为异常标记，不能静默改写 CacheKeeper 的真实逻辑计数。
- 统计与删除也不是完全同一套跳过规则：统计会检查更深层 `/webkit`、`/httpstorages`、`/cookies`，删除分支主要检查 Caches 直接子项后移除；不能把它当成口径一致的证明。

许可证：[MIT](https://github.com/o2ol/clearnbox/blob/c50bc0153409717aad211856554a7eed5860fdd6/LICENSE)。直接复制需保留对应版权与许可证声明。本轮没有复制代码。

## Caz：诊断输出最有价值，清理策略不能整套套用

源码：[RootHelper/main.c](https://github.com/JohnJailbreak/Caz/blob/56e309937f8a8ab886925bbc70c8140994d7b83f/RootHelper/main.c)、[CleanerModel.swift](https://github.com/JohnJailbreak/Caz/blob/56e309937f8a8ab886925bbc70c8140994d7b83f/Caz/CleanerModel.swift)、[RootSpawn.m](https://github.com/JohnJailbreak/Caz/blob/56e309937f8a8ab886925bbc70c8140994d7b83f/Caz/RootSpawn.m)。

- root helper 输出 `CAT / APP / SKIP / STEP / PROG / DONE / SAVED / FREED` 等分型事件。对我们最直接的启发是“每个阶段有结果和失败位置”，不是只给一串总大小。
- `tree_dir`（约 926 行）按 `st_blocks` 统计，并在硬链接分支用设备号+inode 避免重复；同时跳过正在写的导出文件。值得借鉴统计不变量。它的导出遍历范围远大于用户配置的 APP，会暴露完整路径且体积很大，不适合原样发送诊断。
- `walk`（约 158 行）使用 `FTS_PHYSICAL | FTS_NOCHDIR | FTS_XDEV`，限制符号链接跟随和跨卷；这些是文件遍历有用的边界。但它仍通过路径 `unlink`，不是 CacheKeeper 已有最终属性核验/受控范围的替代品。
- 特别区分：`tree_dir` 的硬链接去重不等于 `walk` 的删除计数也去重。`walk` 对每个成功 unlink 累加 `st_blocks`，共享 inode、仍有外部链接或打开句柄时不能据此断言实际释放量。
- `k_keep`（约 312 行）对 TikTok 的 `offline-mode`、`com.studio.album.importToEdit` 等作例外；说明具体 APP 规则值得维护，但这里没有 APP 版本/恢复证据约束。TikTok 的 `com.zhiliaoapp.musically` 不等于国内抖音，不能直接映射。
- `app_cache_targets`（约 563 行）定位 SafariViewService 的 **NetworkCache**，比泛称 WebKit 更细；这可作为未来逐子树验证的研究线索，不意味着百度网盘的 `Library/Caches/WebKit` 整棵安全。
- 下载临时文件策略使用文件名加“一小时未修改”，安装包规则覆盖 `Documents/Inbox`，还包含最近删除、系统缓存、进程关闭及 log trim。这些超出当前 CacheKeeper 的 APP 缓存目标；年龄不证明文件被放弃，不能导入。
- README 写明 iOS 17.0 真机使用、iOS 16 尚未真机验证。TrollStore persona root helper 与 RootHide 插件注入是不同执行链路，不能靠复制 entitlements 获得等价兼容性。Caz 的 YouTube 是 UI 初始排除，可由用户重新开启；Spotify 是强制跳过，不能混为一谈。TikTok 离线/草稿、Strava 离线地图和 Google Maps 离线区域是可借鉴的精确保留候选，已在 CacheKeeper 规则表增加只保留范围，但仍须匹配 APP 构建并真机验收。

许可证状态：当前仓库树没有项目总 LICENSE；仅有 [LICENSE-Dopamine.txt](https://github.com/JohnJailbreak/Caz/blob/56e309937f8a8ab886925bbc70c8140994d7b83f/Caz/Resources/LICENSE-Dopamine.txt)，不能视作对全部 Caz 代码的授权。因此本轮只借鉴思路，独立实现。

## iOSCleanerPro：没有清理代码可拿

[固定提交树](https://github.com/Gle-Res/iOSCleanerPro/tree/f6d79f1e81058333fe21177fd30f2d4d5d908b05)只有 README 与 MIT LICENSE，没有 Swift/Objective-C/C 实现、工程或清理规则。不能从“无需越狱”“一键清理”等介绍推导出权限能力、算法或数据安全性。

## TrollCleaner：诊断分态可参考，释放量与回收站不可用

源码：[CleanupManager.swift](https://github.com/solopais/TrollCleaner/blob/07c87b9d525a71efb721c59e82fb24c4adf3f11c/Sources/TrollCleaner/Utils/CleanupManager.swift)、[DiagnosticsService.swift](https://github.com/solopais/TrollCleaner/blob/07c87b9d525a71efb721c59e82fb24c4adf3f11c/Sources/TrollCleaner/Utils/DiagnosticsService.swift)、[FileScanner.swift](https://github.com/solopais/TrollCleaner/blob/07c87b9d525a71efb721c59e82fb24c4adf3f11c/Sources/TrollCleaner/Utils/FileScanner.swift)。

- `DiagnosticsService.probe` 区分不存在、访问失败、空目录、有内容，可参考。仅取前三个名字的样本不等于深度覆盖；原始样本名称也不宜直接发送。
- `deleteItems` 先移到同设备回收站就增加 `freed`；`deleteDirectoryContents` 与 `emptyTrash` 也有先累计再删除的分支，主 `cleanApp`/微信清理直接删，不统一走回收站。README 的“支持恢复”在当前源码中没有对应恢复方法，不能当作已实现事务。
- 回收站目录按本地时间命名，目标使用 APP 名+文件名，同名冲突可能走直接删除分支；不能作为可靠恢复事务。`cleanApp` 与微信专项调用直接删除目录内容，也不统一经过该回收站。
- 微信专项是硬编码路径（如 `Caches/MMResourceMgr`），缺少版本、索引依赖和恢复证据。名字里含 Cache 不足以证明每个资源可再下载。
- 默认和 safe 配置均启用 `clearCache`，`cleanWeChat` 先清父级 `Library/Caches`，再处理各专项开关；因此 `MMResourceMgr` 的专项开关关闭不能保证保留。CacheKeeper 已单独收紧 `com.tencent.xin` 的该子树；`com.tencent.xin.WebKit` 原本已被必要状态规则保留，不能说三个目录都已被平台清理覆盖。
- `FileScanner` 用递归文件长度、忽略隐藏项和读取异常，没有完整覆盖与硬链接去重口径；不能用于替换当前诊断统计。
- 当前树没有项目总 LICENSE，README 也未给出代码复用许可证。只参考思路，不复制源码。

## 真机证据如何影响下一步

### 百度网盘 13.37.5

15:33 的回执：整目录保留 5 处（WebKit 相关 4 处和 nsurlsessiond），延期 157 项 / 15.00 MB，删除 0。15:33:56 深度检测仍在分批读取；普通文件 215 / 15.37 MB，硬链接 120，孪生样本与来源均截断。多数普通文件年龄不足 60 秒。它们分别表示规则保留、年龄延期和未完整扫描，不能归成一个“没有清理权限”。

已显示的 WebKit Blobs/Records 孪生两端在同一 Caches 子树；最大硬链接有两个 9.26 MB 路径。不能据此认定所有链接都在该范围，也不能把 9.26 MB 等同于用户的 8.3 MB PDF。PDF 能离线完整打开只证明本地仍有可用内容，物理路径和云端可恢复性仍未落实。

后续应使用统一报告对照 APP 版本、扫描时间、保留子树、最大普通/硬链接、覆盖状态；针对精确资源验证。四个第三方仓库均未提供这个 PDF 的直接证据。

### Swiftgram

15:35–15:36 截图：`Group/group.app.swiftgram.ios/telegram-data` 约 898.59 MB；主 `postbox/db/db_sqlite` 577.81 MB，另有 WAL 和媒体。深度过程中普通文件统计增加到 2576 项，跳过 2600 个硬链接；可见大量资源与 `_partial` 成对，最大示例 9.07 MB / nlink 2。孪生搜索失败 1 项，来源与显示都截断。

这证明该共享根混有大数据库和资源文件，不证明整个根或所有 `_partial` 文件是垃圾。主数据库、媒体索引与云媒体需要分开适配；共享根还受扩展使用。报告中“尚无清理回执”与页面“仅供分析”一致，不能把该体积波动称作 CacheKeeper 删除。采集导出会把账号段和资源标识替换为报告内一致的别名，避免继续发送私人路径。

## 本轮落地

最初实现统一报告与串行补采；真机反馈表明全量深度队列过重，后续改为固定 APP 数量的已有记录汇总。采集仅在内存，用户手动导出才生成分享文件，保留缺失/失败/部分/历史状态和覆盖/截断标记。具体 APP 的目录/深度检测保持独立入口。输出仅技术路径结构和统计，不复制文件内容或原始日志；用户手动分享一个 JSON。首页搜索同时修复布局与手势边界。百度网盘 PDF、Swiftgram 非标准媒体清理仍需要报告和恢复验证，不在此分析中宣布适配完成。

2026-11-14 再复核后：旧布局/手势调整未解决用户反复发生的搜索异常，已将来源读取与输入分离并补齐损坏数据校验。四仓库中能够独立落地的精确保留信息已进入单一规则表，范围为 TikTok 离线/草稿、Strava/Maps 离线区域、微信 MMResourceMgr 与 Spotify Library/Caches；不改变用户开关，也不凭第三方注释扩大删除。原报告、用户理解和复核差异已分别保留，不把本地私人报告提交到仓库。

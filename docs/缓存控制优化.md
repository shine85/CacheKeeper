# 缓存控制与数据目录

适用目标为 iOS 16–17 RootHide；Dopamine 设备仍需核对使用的是 RootHide 兼容注入环境。系统设置中的“文稿与数据”是存储占用，不是可删除缓存总量，可能包含聊天、账号、离线下载、数据库及业务资源。

## 模式

应用列表显示系统注册的已安装 APP（包含系统 APP 和第三方 APP），按 Bundle ID 去重，回到页面时重新读取。未配置、只有目录记录、总开关关闭或状态损坏均不启用；不对微信等 APP 硬编码特殊名单。0.5.1 起用户直接打开某个目录，或点击“一键开启”，会同时打开当前 APP 总开关，不再弹二次确认；检测、切换模式和网络选项不会开启总开关。总开关已开启但没有文件清理目录时，网络功能仍按独立选项执行。

0.6.0 的“一键开启”是明确的全套预设：选中检测到的可管理父目录、总开关开启、切到自动模式、网络磁盘缓存限制开启、新增缓存自动发现开启。保存后回读核对并在页面显示结果。单项开启保留原模式与网络选项。模式用三段单选直接切换；选择自动/只禁止会开启网络选项，只清理暂停网络限制。网络开关可随后单独关闭。

从未开启网络禁止的 APP 不安装 NSURLCache Hook、不初始化共享缓存、不写网络状态。已开启后再关闭时仅恢复本插件改变过的容量；重复关闭不再改写容量。通用注入仍需读取开关并监听配置通知，因此“未开启不管”指不改变网络缓存及不清理文件，不能解释为 dylib 完全未加载。手动快捷清理同样受总开关与模式约束。

| 模式 | 标准 NSURLCache | 文件清理 |
| --- | --- | --- |
| 自动 | 按独立网络开关决定；开启时磁盘容量置 0 | APP 完全退出后处理所选目录，网络限制失效不阻断清理 |
| 只禁止 | 同上；网络开关关闭时不执行缓存干预 | 不执行文件删除，手动快捷操作也受此模式约束 |
| 只清理 | 恢复 APP 原本请求的磁盘容量 | APP 完全退出后处理所选目录 |

网络禁止保留内存缓存、Cookie 和请求缓存策略；仅影响标准 NSURLCache，不能阻止 WebKit、视频 SDK 或 APP 自建文件缓存。可能增加流量、重复加载耗时及电量消耗，降低离线访问能力，不能保证每个 APP 的行为不变。关闭模式恢复容量，不恢复此前已被框架淘汰的缓存。

Apple 的 [diskCapacity 文档](https://developer.apple.com/documentation/foundation/urlcache/diskcapacity) 说明：降低容量会按需收缩磁盘缓存。本插件不调用 removeAllCachedResponses；容量调整可能由系统即时淘汰自身网络缓存，这与退出后文件清理的 60 秒保护是两条不同机制。

## 扫描目录与处理边界

0.6.1 起 APP 总开关不默认选择任何目录，`Library/Caches`/`tmp` 也不预选；已有用户选择保持原样。只有单项、一键开启或明确授权自动发现才纳入目录。单独开启总开关也不会替新 APP 打开网络选项。

## 推荐使用顺序与新增文件

1. 安装目标 APP，打开一次并正常使用，然后从多任务划掉，确认它退出。
2. 在缓存管家找到该 APP，进入详情点击“检测目录”。可管理缓存按已选置顶、组内占用降序排列；混合/共享数据与用途未知目录各自折叠。已知敏感持久化目录隐藏。有可管理目录后点击“一键开启”，应用上述全套预设，无二次确认。单项开启同样直接保存。
3. 自动或只清理模式会检查首次使用期间已经生成的缓存，不存在“开启之前一律保留”的基线；满足创建/修改/ctime 均超过 60 秒、完整数据预检、媒体内容识别等条件才删除。只禁止模式不删除文件。
4. 已选父目录内新增文件和子目录自动覆盖。开启“自动纳入新增缓存目录”后，对已启用且完全退出的 APP 约每 30 秒检查固定缓存根：`Library/Caches`、`tmp`、`Library/Logs`、顶层 `Caches`/`Cache`/`cache`/`.cache`，新出现的这些根自动纳入。取消某目录会保存排除，自动发现不会再开；主动重新开启它或再次一键选中它才解除该项排除。新出现的任意业务目录不会自动变成可清理目录。

运行一次通常会产生缓存，也会产生登录信息、数据库和必要资源，不能保证每个新文件都无用。60 秒是最低保护时间，实际处理还取决于进程退出、扫描进度和后续检查周期。目的是减少可重建缓存占用，不是清空“文稿与数据”；未知内容不因新产生或体积大而被删除。

| 目录 | 常见内容 | 本插件处理 |
| --- | --- | --- |
| Library/Caches、顶层 Cache/Caches/cache/.cache | 图片、音视频、网络与 SDK 缓存，也可能混有数据库 | 可选择；只删除识别为媒体内容且满足时间条件的普通文件 |
| tmp | 下载中转、解压、导入导出、临时工作文件 | 可选择；同样保守判断，不因处于 tmp 就全部删除 |
| Library/Logs | 诊断日志及组件状态 | 展示占用；未知文本、二进制或数据库 WAL 保留 |
| Library/Application Support | 混合用途：业务数据库、离线资源、运行组件，也可能有缓存 | 混合用途待确认，不自动处理 |
| Documents、Inbox、Downloads | 用户文件、聊天附件、导入内容、离线下载 | 隐藏，不锁不删 |
| Library/Preferences、Cookies、WebKit、Keychains | 配置、登录态、网站数据 | 隐藏，不锁不删 |
| Library/HTTPStorages | 网络持久化数据，可能混有会话状态 | 混合用途待确认，不自动处理 |
| Library/SplashBoard、Saved Application State 及其他实际存在的目录 | 启动快照、状态恢复或 APP 自定义数据 | 仅查看，不猜测可删除性 |
| Group/<组ID>/… | 主 APP、小组件或其他进程共享数据 | 仅统计和 Filza 跳转；执行端禁止清理 |

扫描实际存在的主容器和系统返回的 App Group 一级目录与 Library 一级分类，不递归生成目录行，无固定 150 项截断；父目录已列出时忽略后代，同一共享地址在单个 APP 内去重。目录页按占用降序并标明处理范围，支持 Filza 跳转。检测时间按剩余目录分配，超时标“大小未统计完”。共享 API 不可用或权限不足时无法统计完整范围，不能推定不存在共享数据。

未知目录不再归为已确认业务数据：单独“用途未知·待分析”区显示数量与已统计占用，明确尚无证据证明它是缓存或必需数据。“混合用途与共享数据”是独立只读区。两区均不参与自动清理，不宣称每个文件都必需；公认敏感持久化目录在扫描和旧快照展示两端过滤。自动发现只检查固定缓存根，关闭后仅管理用户明确选择。

## Filza 跳转

Filza 5.0.1-3 官方 RootHide 包没有注册 `filza://`，因此旧跳转可能失败。0.6.1 读取实际安装信息：有 scheme 的版本使用原 URL，无 scheme 的版本按 Bundle ID 投递文件 URL；失败显示具体系统错误，并可手动复制路径。证据及验证边界见 [Filza 5 兼容核验](Filza5兼容核验.md)。请求成功不代表已观察到目标目录显示，仍需手机确认。

## 清理不变量

- 仅所选且开启的 APP；只在 SpringBoard 可确认进程退出时清理。状态未知、APP 重新运行、开关或容器改变时取消。
- 创建、修改及元数据变更时间都至少 60 秒；缺少可靠时间的文件保留。已有缓存原地追加同样受保护。
- 数据库、登录态、Documents、Preferences、WebKit、Cookies、下载/离线内容及其子目录排除。扩展名和“体积增长”都不证明可以删除。
- 先完整预检，再删除；两阶段都保留分批进度。直接含数据库/登录标记、SQLite/bplist 文件头、LevelDB 标记的目录及后代整体保留。预检失败或目录身份/修改时间改变时跳过；如果缓存根本身含数据库，会保留整个根，避免破坏配套数据。
- 保守识别 PNG/JPEG/GIF/WebP、ISO 媒体、WAV/Ogg/FLAC/ID3 文件头；无扩展名文件只有内容可识别才处理。未知 .cache/.tmp/.log 不删除，避免误删 LevelDB/RocksDB WAL 和私有状态。
- 不删除目录、不跟随符号链接、不处理硬链接。文件身份、时间与路径在删除前复核；不保证识别任意 APP 的私有数据语义。
- 不再对目录 chmod 限写：锁父目录会连带阻断受保护文件创建，无法满足“数据库与登录态永不锁”。启动时恢复旧版权限记录，并按 inode/device 防止恢复到已更换的目录。

## 结构与兼容

directories.plist 保存明确选择；appEnabled.plist 保存 enabled、mode、urlCache、autoDiscover、excludedPaths。引擎按“明确选择 + 实际发现的固定根 - 用户排除”计算范围，不把自动发现结果回写为第二份用户选择。旧记录自动发现默认关闭，升级不扩大范围；一键开启或手动开启自动发现才授权扩展。面板是唯一配置写入方，不可读的原配置拒绝覆盖。跨方案安装应重新确认模式及网络选项。

Scanner.m 串行处理分批遍历并保留进度；状态累计量同步读改写。列表与详情共享 Status/<bundle>.auto.plist，网络进程单独写 Status/<bundle>.network.plist。回执是最近报告，不能替代当前设备注入与网络抓包验证。

## 标准缓存全量清理（按 APP 开关，2026-11-11 对话确认）

用户在真机验证基础清理后确认：新增按 APP 的「标准缓存目录全量清理」开关（状态键 `fullClear`，默认关闭）。开启后，该 APP 完全退出时，其已选中的平台缓存契约目录（`axs_cachekeeper_directory_kind == cache` 的白名单根，如 Library/Caches、tmp、Caches 等）内的普通文件全部删除，不再按媒体签名、数据标记名或 SQLite/bplist 文件头保留；仍保留的底线：APP 必须完全退出（FBProcessManager 判定 Stopped）、文件三个时间戳均超过 60 秒、单链接、非符号链接、删除前身份与快照核对、预检后变化的目录跳过、手动排除与未选目录不处理、目录本身保留。

与 0.7.0 取舍的关系：Library/Logs 已归混合类（可能含 WAL），不属于 cache 根，全量清理不覆盖；未知/混合目录不因本开关放宽（仍只有深度检测档案，没有隔离与人工判定删除）；一键开启、模式切换、总开关保存都不写 `fullClear`，只能由用户在详情页逐个 APP 打开，创作类 APP 保持默认关闭。风险已在开关说明中明示：草稿、离线下载若存于这些缓存根会一并删除。原生测试覆盖开关默认/保留/作用域判定与全量清理夹具（普通模式整根保留 vs 全量模式 5 个文件全删、目录保留）。

## 只禁止模式目录写锁（2026-11-11 用户确认，推翻 0.7.0 不加 chmod 的取舍）

用户在真机使用中明确「禁止」的定义是运行中也不往缓存目录放任何东西；标准 NSURLCache 置 0 达不到这一点。故自本轮起：APP 已启用且模式为「只禁止」时，其已选中的缓存根（与清理同一组有效路径）在 APP 完全退出后被递归写锁——根、子目录与普通文件逐项记录原始权限（permissions.plist，格式与旧版记录相同）后去掉全部写权限，可读不可新建/修改；符号链接不跟随。切换到其他模式、关闭总开关、取消选择或卸载时，桌面进程按「期望锁定集合」对账：期望外的记录每轮恢复，ckrestore 卸载时全量恢复。锁定逐项核对 inode/device 后 fchmod，中途失败回滚本轮改动；签名（根集合）不变时 30 秒内不重复上锁，但被 APP 自行改回的权限会在下个周期补锁。状态回执区分：已锁定/未完全退出待执行/锁定失败/无可选目录。原生测试覆盖锁定生效（追加与新建被拒）、链接外文件不受影响、重复锁定不覆盖原始记录、按记录精确恢复目录与文件。

边界不变：自动、只清理模式不锁定；锁定不删除任何已有文件；全量清理（fullClear）与只禁止互不影响（只禁止不做清理）。已知代价（已在模式说明中写明）：把中转文件写入 tmp/Caches 的正经功能（分享、导出、上传暂存、草稿自动保存）在锁定期间会被系统拒绝，可能报错或静默失败；这是用户在知情后选定的语义。

## 删除路径形态修复（2026-11-11 真机 errno 22 全灭后）

真机 v0.7.0-25.1 首跑全量清理：263 项删除全部失败、errno 统一 22（EINVAL）、removed 0。此前普通模式从未真正走到删除调用（内容被数据目录门挡住），该问题才在全量清理下暴露；macOS 原生测试全过，属真机路径形态差异——容器根为解析符号链接后的 /private/var/... 形态，删除入口的父路径字符串直比可能把根内文件整批误判为根外。

修复（通用，作用于全部 APP 与全部缓存根的 Sweep 删除路径，非单 APP 补丁）：

- 删除入口父路径校验改为多形态匹配：根路径的原形、标准化形、解析形、解析后标准化形四种形态任一命中即视为根内，相对路径按命中形态切分。
- 删除失败报错细化到阶段：路径校验 / 打开缓存根 / 缓存根已变化 / 打开子目录 / 文件已变化 / 文件状态已变化 / 删除文件，各带 errno；回执可直接定位，不再只有一个总 errno。
- 原生测试新增「嵌套数据子树」夹具（数据文件在子目录内、根级有散落媒体）：普通模式只删根级媒体且整棵子树保留；全量清理删净子树内全部文件、failed=0、无阶段错误、目录保留。

## 打开目录的链接语义修复（2026-11-11 真机 errno 20 接续定位）

v0.7.0-26.1 真机复验：阶段化报错生效，删除失败定位到「打开缓存根（errno 20 ENOTDIR）」、270 项。根源在 axs_cachekeeper_open_directory 的逐级打开：它对每一级组件都用 O_NOFOLLOW，等于把每个中间组件都当末级处理——路径中任一中间组件是符号链接（如 /var→/private/var、越狱根链接等系统形态）就以 ENOTDIR 失败；而内核路径解析与 NSURL 枚举会跟随中间链接，所以检测/发现/预检全正常、唯独删除入口的逐级打开全灭。发现函数对 ENOTDIR 的静默容忍使该问题在发现环节不留痕迹。

修复（通用，FileAccess 共享函数，清理/权限恢复/深度检测共同受益）：逐级打开时中间组件按内核语义跟随符号链接，仅末级目标保持 O_NOFOLLOW；各调用方原有的身份核对（inode/device、快照）不变，替换中间链接只会触发身份不一致中止，不会误删。删除「打开缓存根」失败时回执附带首个异常组件名。原生测试新增链接中间层回归：经链接打开子目录成功、末级本身是链接仍拒绝。

## 对照 AppDataCleaner 方案吸收四项（2026-11-11，用户确认）

经逐条对照梳理（对照表另存），用户确认吸收以下四项，本节为落地定义：

1. **进程实例绑定**：清理任务绑定「刚退出的进程实例」（Bundle＋PID＋进程启动时间，取自 FBProcess 的 pid 与 sysctl KERN_PROC_PID 的 kp_proc.p_starttime；iOS SDK 无 libproc.h，proc_pidinfo 路线已在构建 #28 证伪并改用 sysctl）。引擎在每轮入口独立观测各已启用 APP 的当前运行实例（不受清理忙碌状态影响），任务创建时把最近观测到的实例写入任务签名与绑定字段；续跑复检时若观测实例与绑定不一致，判定旧任务过期并停止。取不到启动时间则不绑定（退回仅按进程状态判定），不用仅 pid 的弱标识冒充绑定。本引擎任务按 Bundle 建模，PID 复用的直接风险不在任务键上，此绑定主要防「任务存续期间新实例启停后又退出、旧任务误删新实例缓存」的错位，60 秒新鲜度规则仍是第一道防线。
2. **信号置信分级（形式补齐）**：单一信号源（FrontBoard 进程清单）下，清单完整且目标消失＝强信号；接口不可用/清单无效＝无信号。清理入口显式要求强信号才允许进入删除路径；将来若引入弱信号源（如定向轮询兜底），只能作辅助确认，不得单独触发清理，分级收口在 AxsCacheKeeperProcess.h，不分散到调用方。支持范围维持 iOS 16–17.3.1，不做分版本 Adapter（用户决策）。
3. **单轮清理硬上限**：单轮累计删除 ≥2000 项或累计运行 ≥120 秒即收尾，状态注明「已达单轮上限…顺延下轮」，剩余内容下轮重新完整预检后继续。数值按本引擎「每周期推进 256 项」的分批模型适配（方案原案 2000 项/30 秒中的时长按本模型放宽至 120 秒累计），上限的意义是限制单轮异常的损害半径。不设单文件大小上限：视频类缓存文件常超 50 MB，设限会误伤正常清理。
4. **Dry Run 三准则（验收纪律，成文）**：今后任何「扩大清理范围」的变更（新增可清理目录类别、放宽内容规则、扩大 fullClear 适用面等），推送前必须对代表性 APP 走完三准则并留档：①零保护误报——深度检测标为可清理的路径抽查确认无一属于保护类别；②使用-再扫描对比——正常使用 APP 前后各做一次深度检测/快照对比，候选清单稳定性可解释；③假设删除影响评估——对候选逐项回答「删后下次启动会发生什么」，答案不是「会重新生成/不依赖」的一律移出范围。三准则结论不跨 iOS 大版本复用，系统大版本升级后重走。

未采纳项（与用户既定决策冲突，定格）：整体重构/更名、iOS 15 与分版本 Adapter、子目录白名单替代内容规则、tmp 24 小时阈值、禁止 chmod(用户已定写锁并入只禁止）、Caches 内数据库绝对保护（用户已定 fullClear 按 APP 开关知情全清，标准模式下数据库仍受保护）、独立 Helper（容器访问已由真机事实结案：SpringBoard 侧引擎可正常删除，历次失败均为路径形态而非权限）。

## 日志目录定级通道（2026-11-11，用户确认的通用机制）

背景：抖音文稿与数据对账发现，其 Library/alog（字节诊断/埋点日志，约 19.45 MB）等自定义目录属用途未知类，标准规则不处理。用户决定「摘」且明确不只针对单个 APP，故落地为全插件通用机制，不做任何按 APP 硬编码：

- **定级入口**：用途未知目录的「目录档案」页（深度检测）提供「定级·日志」动作。证据门：必须已有一份完成且读到至少 1 个普通文件的档案才可定级；读到 0 个文件（如 Library/Pitaya，内容全在被跳过的敏感子目录中）提示证据不足、不可定级。
- **定级范围校验**（axs_cachekeeper_log_path_valid）：仅 kind=unknown 的相对路径可定级；受保护路径、缓存/混合/共享类不可；任何受保护根或标准缓存根的祖先路径（如 Library 本身）不可，防止一次定级吞掉整片区域。
- **存储**：定级清单存于该 APP 状态键 logPaths，经 axs_cachekeeper_app_state 在所有状态保存中保留；一键开启与自动发现永不写入；用户可随时取消定级（详情页未知区行开关或档案页按钮）。
- **有效根**：axs_cachekeeper_effective_paths 将定级目录与缓存根并列纳入（仍受手动排除约束）；只禁止模式的写锁期望集合只取 kind=cache 的根，定级目录不被上锁。
- **清理规则**（Sweep logMode）：与标准模式共用两阶段预检、数据标记整树保护、身份/快照复核与 60 秒门槛；删除内容门在数据库/bplist 头否决之上叠加——文件名必须命中日志特征（.log/.alog/.xlog 后缀或复合后缀，如 *.alog.iOS.1128），且文件名不得命中数据标记（含数字主干的 .log 等 LevelDB 形态被否决）。媒体文件、文本文件在定级目录内一律保留。
- **回执与界面**：完成文案对含定级根的轮次注明「含用户定级的日志目录」；逐目录回执照常记录。详情页未知区已定级行显示定级状态与关闭开关；档案页显示定级状态行。
- **验证**：原生测试覆盖定级校验/有效根/状态保留/定级保存往返，以及日志模式夹具（仅 3 个日志文件被删，媒体、文本、数据子树含其内日志全部保留）。真机首验样本为抖音 Library/alog（预期约清 19 MB 日志、数据名文件保留、功能无感），验过后其他 APP 的同类目录（如微信 *.xlog）照此逐个定级。

## 日志模式文件级稳定性门（2026-11-11，用户拍板）

真机首验（30.1）：抖音 Library/alog 定级成立，但首轮删除 0——预检后 14 个目录被判变化。alog 是热目录（检测间隔 3 分钟内文件数 178→190、33 个文件不足 60 秒），兄弟文件的持续增删使目录级稳定性门（目录快照全等＋目录内全部文件复核）整轮空转。这也是与 AppData 手动清理的实际差距所在：它没有这道门。

修法（仅日志模式 Sweep logMode）：删除前目录复核降为身份核对（inode/设备号），文件自身稳定性改由逐文件比对预检记录保证——记录缺失（预检后新增）或已变化的只跳过该文件并计入变化数（errno EBUSY，不计失败），不连坐同目录其他文件。标准模式与全量清理维持目录级门不变（APP 真停后目录安定、靠重复轮次自愈，已有真机证据）；数据标记整树保护、60 秒门槛、内容门（日志名特征＋数据否决＋SQLite/bplist 头否决）均不变。原生测试新增热目录夹具：日志模式下兄弟改写只跳过自身（删 2 留 1），全量对照整目录保留（删 0）。

## 日志模式二修：文件级数据保护＋祖先链记录键（2026-11-11，31.1 真机复盘）

31.1 真机复验仍删除 0，回执给出两个决定性线索：受保护仅 3 项（＝被整树跳过的目录条目数，其内文件根本未被枚举）、末尾错误为新版的目录身份核对失败。据此定案两处缺陷：

1. **预检数据标记的目录级连坐（主因）**：标准模式下「目录内出现数据文件→整目录判数据」对日志目录是误伤——alog 的 ready/ 里日志与数据名文件混放，一个 0.02 MB 的数据名文件即毒化整棵子树（约 170 个日志文件未被枚举）。日志模式改为**文件级数据保护**：预检把数据名/SQLite·bplist 头/预检失败的文件只标记自身（dataFiles)，删除时再由内容门复核（日志名特征＋数据标记名否决＋SQLite/bplist 头否决不变）；目录自身名称命中数据标记的仍整树保护。标准模式维持目录级（其语义是数据附件成组保留），不变。**语义修正声明**：此前「定级目录内数据子树整树保留」的表述自本轮起对日志模式改为文件级——数据文件本体受双重保护，但其旁的日志文件照常清理；原生测试中 vault 夹具的 inside.log 预期随之翻转（删），inner.sqlite 不变（留）。
2. **祖先链记录键形态不一致**：删除时按 root 拼接的构造路径查目录快照，与枚举器给出的目录路径形态在真机上可能不一致（尾随斜杠等），深层文件（alog 为四级嵌套）在祖先复核处全灭；浅层文件不受影响，这也解释了标准模式历轮「若干目录判变化」的残留。修法：目录快照记录键统一 stringByStandardizingPath；祖先链复核键改为由 parent（枚举器形态）逐级剥组件得到；复核失败原因细分为记录缺失/目录已被替换/读取失败并写入回执（verifyDetail)，下一轮真机若仍有残留可一击定位。

原生测试新增：混放目录夹具（纯日志删 2、数据名与 SQLite 头文件留）、四级嵌套日志夹具；热目录 A/B 与既有日志用例保持。

## 进程门细分：挂起稳定放行（2026-11-11，用户拍板 A 案）

真机定案：APP 被划掉后常被静默推送/后台刷新唤醒，干完活被系统挂起（suspended）而非终止，FrontBoard 记录长留数小时；旧判定「清单有记录＝在运行」使自动清理无限期停摆（抖音 Caches 满置 54.52 MB、用户确认已划掉且未再打开、无任何新轮次）。

新判定（AxsCacheKeeperProcess.h `axs_cachekeeper_process_exec_state`，完整清单 fail-closed 前提不变）：Absent（无记录）／Executing（taskState=1）／Suspended（taskState=2）／Unknown（接口缺失、状态读不到、taskState 其他值——reason 带原始值供真机定位）。放行规则（Scanner.m）：Absent 照旧；Suspended 须同一进程实例持续挂起满 60 秒（入口观测维护 bundle→{identity, since}，实例变化即重置），且任务的 shouldContinue 逐项以同一规则复核（`axs_cachekeeper_gate_open`，含任务实例绑定）——挂起进程被内核冻结、不能执行，平台契约亦允许清其缓存；Executing 与 Unknown 永不放行。状态文案同步细分：挂起确认中／挂起满 60 秒按已退出处理／状态无法确认（taskState=N）。原生测试以假进程对象覆盖四态与 fail-closed 分支；60 秒稳定性为 Scanner 主线程簿记，无原生覆盖，真机以「划掉后不重开、2–3 分钟内出现新轮次回执」验收。

## 未知目录自动清理（B 案，2026-11-12，用户拍板）

治理修订：用户先后否决两条人工路线——逐目录手动删除裁决（「都人工了还玩什么插件」）、隔离观察（文件仍在手机上占空间，与腾空间目的相悖）。最终口径：**无数据证据的未知目录，退出即清，全程插件自动判断**；唯一用户动作仍是逐 APP 总开关。

机制（Baseline.m purge 模式＋Scanner 候选集）：每轮为已启用 APP 扫描未知目录候选（30 秒缓存，Group 只读不入选；已定级日志目录走日志模式、手动排除者不入选），Sweep 预检即全目录内容审查——数据标记名、受保护路径成分、SQLite/bplist 文件头三者任一命中，整根出局（purgeBlocked，回执写明首条证据路径，不计失败）；读不到内容同样出局（审不完不删）。零证据的目录按文件级稳定性门全清（媒体、文本、运行时文件皆删），仍守 60 秒年龄、身份核对、nlink==1。证据口径（Policy.h `axs_cachekeeper_purge_evidence_path`）：数据库与登录态类算证据；**配置类 .plist/.json 不算证据**（可再生运行时配置，tma 含此类文件仍可清）；凭证类 .key/.pem/.p12 算证据。删除用文件级门（与日志模式同档），不用目录级门。

盲区（已向用户明示）：长得不像任何东西的用户数据（自定义二进制存档、裸文档、离线媒体）会通过审查——这是纯 B 方案固有的代价。兜底：逐 APP 开关（未开启的 APP 碰都不碰）＋每轮按目录回执（首轮即可发现异常并关停该 APP）。定级通道仍保留，只用于日志与数据混放的目录（如 alog）。

联动改动：全新 APP 默认自动发现开启（Policy.h `axs_cachekeeper_auto_discover` 缺键默认 YES；已明确关闭的保持关闭）——只开总开关即全自动，标准缓存根自动纳入、未知目录自动审查；一键开启语义不变。详情页文案同步：未知分区不再写「不自动处理」，改为内容审查说明；回执追加「未知目录已按内容审查清理…」一行。

原生测试（tests/cache_control_tests.m）：零证据目录全清 4 文件（含 .json/.plist 配置）；伪装 SQLite 头文件整根出局零删零失败；含 Preferences 子目录整根出局；热目录文件级门（兄弟变化只跳过自身）；候选集过滤（已定级/缓存根/受保护目录不入选）；全新 APP 默认自动发现开启、已关闭者保持关闭。

## 未知目录逐项保留开关与分区顺序（2026-11-12，用户提问后补）

分区顺序：详情页「用途未知」分区上调至第 2 分区，「混合用途与共享数据」下调至第 3 分区（行映射、标题、脚注、展开开关同步对调）。

开关问题（用户原问：未知目录是否每项需要一个开关，插件如何知道清理还是禁止）：此前未知目录行确实没有开关——B 案的清理与否由退出时内容审查自动决定，不需要逐项手动定级；定级只用于日志与数据混放目录。但这留下一个缺口：想保住某个未知目录只能关整个 APP。补「保留开关」：未定级未知目录每行一个开关，默认开（参与自动内容审查）；关 = 写入排除清单（`excludedPaths`），退出时整目录不做内容审查、不清理。已定级目录仍用定级开关；只禁止模式下未知目录既不删除也不锁定（写锁只覆盖已选标准缓存根）。

## B 案候选发现修正：readOnly 陷阱（2026-11-12，#37 真机静默失效）

#37 真机：抖音与极速版划掉后台近 20 分钟，未知目录纹丝不动，回执亦无内容审查行。根因：Scanner 候选发现用 `scan_targets` 并以 `readOnly==NO` 过滤——但 `scan_targets` 的 readOnly 标记的是“非标准缓存路径”（`@(!cache_path)`），未知目录全是 readOnly=YES，过滤后候选集恒为空，B 案一次都没跑过；回执无行、累计增长全是标准缓存周转。修正：新增 `axs_cachekeeper_purge_candidates`（直接复用 `scan_directories` 的相对路径串），Scanner 改调它；类型/定级/排除的过滤仍在 `purge_paths`。原生测试锁定回归：夹具家目录的枚举须含未知目录，且 `purge_paths` 只保留未知目录。教训：scan_targets 的 readOnly 是详情页“是否给开关”的展示分类，不是文件系统只读，任何清理候选逻辑不得用它过滤。

## taskState=3 已终止（2026-11-12，#38 真机抖音实测）

抖音划掉约 50 分钟后状态显示「执行状态无法确认（taskState=3），暂不删除」，清理被门拦住。判定：taskState=3 为 RBSProcessTaskStateTerminated（进程已终止）。依据：①既定映射 1=执行中、2=已挂起，iOS 进程生命线为执行→挂起→终止，3 为唯一剩余态；②划掉后的 APP 不可能在后台执行 50 分钟，不可能是执行中；③该态由挂起转入，符合系统回收挂起进程的路径。修正：exec_state 新增 Terminated 态（taskState=3），Scanner 主循环与 gate_open 均按已退出直接放行（无需 60 秒稳定等待——已终止的进程不能执行、不能恢复为同一实例；新实例启动由任务实例绑定拦截）。原生测试锁定：taskState=3 判为已终止，taskState=7 仍判未知不放行。

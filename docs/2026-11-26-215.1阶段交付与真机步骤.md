## 手机集中验收

以下操作由用户在手机上集中进行；本轮开发侧没有连接手机、启动 APP、安装插件或执行 runtime003。

1. 从 214.1 正常覆盖安装上面的 215.1 deb，按包管理器提示完成必要的重启用户空间；确认缓存管家显示 `0.7.2-215.1`。保留原配置、排除项和已有报告。
2. 选择已经验证过 SDWebImage writer 的**米家**，开启该 APP，选择 **“限制缓存并清理”** 模式。沿用现有登录，打开原本就在使用的设备列表或设备详情页；若页面支持刷新，刷新一次，再打开两三个已有设备页面，约 30–60 秒后切后台。不要新增登录、解绑设备、清账号数据或下载重要资源。上述动作只是统一操作负载，是否产生非空 writer 必须以报告为准，浏览本身不算触发成功。回缓存管家点“汇总已保存诊断”→“导出报告”，保存为 `215-01-米家限制.json`。
3. 将米家改为 **“只清理”**，回同一米家进程继续相同操作，再切后台等待至少 60 秒并查看清理回执。汇总并导出 `215-02-米家只清理.json`。这一阶段不手动杀掉米家；若系统自行重启进程，报告会明确另一个进程，不能把两个进程拼成热切换证据。
4. 关闭米家在缓存管家的 APP 总开关，回米家重复相同页面加载，确认图片、原有设备控制和正常使用无可见异常。切后台、汇总并导出 `215-03-米家关闭.json`。结束后如要恢复原配置，先完成本阶段报告再恢复。
5. 在诊断页点 **“重新测量全容器占用 · 只读”**，留在页面等待终态；有明确读取失败也保留实际结果，不扩权、不把失败算零。之后必须再点 **“汇总已保存诊断”**，最后 **“导出报告”**，保存 `215-04-全容器综合.json`。不需要重新遍历每个 APP 目录，也不需要再次手工采安装包。

将四份 JSON 放到仓库 `packages/采集报告/215.1/`（手机先“存储到文件”，再传入此目录），同时用一句话说明三个模式的先后顺序、是否重开米家、是否有可见异常。无需提供账号、Cookie 或文件正文。开发侧复核 schema 3、各 epoch 的非空 attempts/blocked/allowed、总计与子计数、旧记录来源和容量 summary binding；“转交”仍不是落盘成功，整 APP 占用或物理净释放不能只凭该计数判断。

本轮集中操作一次即可；若非空 attempts 仍为 0，开发侧记为未触发并结合后续统一批采分析，不让用户反复清数据或试页面制造计数。QQ、百度、京东、Gurd 等未适配主体不纳入这次手机反复试错；接口与路径由开发侧在获准连接后集中取证。

## 既定方案剩余项与完成条件

- 本组还缺上面 215.1 目标手机报告及全 APP 静态批次实际执行；非空尝试未触发、记录不足和明确失败分别处理，不把 0 当成功。需要新的明确可连接时段后，开发侧集中采一次，runtime/attach 仍须具体窗口授权。
- Gurd 缺全 writer 共同保护域、初始化/加载终态、一致候选快照和真实清前/清后观察；生产保持 `scopeUnproven`、零宿主提交。只有真实范围可证且连续两轮 submitted、before/after complete 才能验收该能力。
- QQ、百度、京东与 Swiftgram 的主体资源仍需各自已证 owner、保留范围、事务/队列和恢复效果。京东已证明旧式单 `SDImageCache` 及永久/自定义路径，与当前四类 5.x 契约不同，不能套用百度固定 legacy。214/215 的库存或 writer 观测修复没有解决这些私有适配。

## 距离最终产品目标的缺口

全部当前 APP 的安全可丢弃资源契约、真实清理与非空写入限制、关闭后恢复、必要数据保持仍须逐能力闭合，并由统一增量核验覆盖新增/升级/资源结构变化。真实空间效果、独占物理归因、iOS 17 目标机和卸载恢复仍未验证。未知资源继续保留，发现或识别不等于取得删除授权，也不能承诺所有 APP 总占用永不增长。

耐久开发证据在本地 `packages/验收证据/0.7.2-215.1/`，包含源提交/run 绑定、下载 digest、原始四组 artifact ZIP、关键日志、包附件和 manifest；不上传私人采集内容。

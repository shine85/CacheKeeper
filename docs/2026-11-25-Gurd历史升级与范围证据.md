# Gurd 历史升级与范围证据

本轮解决已确认的升级缺陷：201.1/202.1 的合法 Gurd 历史没有 `scopeProof`，211.1 仍使用 schema 1 却强制该字段，导致诊断只显示 `invalid`，宿主启动恢复则拒绝整份旧历史并可能写回空历史。该修复保护历史与诊断来源，不代表 Gurd 私有资源清理范围已经证明。

## 实现与不变量

- 新生产回执使用 schema 2。唯一 `axs_cachekeeper_gurd_receipt_decode` 负责版本读取、字段验证和 canonical 投影，诊断、库存、能力摘要和引擎恢复复用同一实现。
- schema 1 的旧 13 字段 operation 仅在其自身 producer 为已发布的 201.1/202.1 且旧字段闭集、类型、状态、采样和差值均合法时迁移。新增的最小标记为 `scopeProof={state:notRecorded,source:legacyReceiptV1}`。保留 event、producer、失败原因、before/after 与历史差值，不补造宿主身份、目录身份或候选摘要。
- schema 2 缺 proof、新 producer 缺 proof、重复事件、额外字段和损坏数据仍明确拒绝。拒绝仅返回封闭 stage/code、operationIndex、原 schema 与验证过的 producer，不输出未知原始字段。
- 混合历史只要包含旧证据缺失标记，库存和能力摘要都显示 `legacyScopeNotRecorded`。新顶层 producer 不会替旧事件补证明。scope marker 不被生产 Source 的 scope proof validator 接受，宿主提交仍要求真实完整谓词证明。

范围证据未知时直接补默认 complete proof 会伪造授权；把历史统一改成空 legacyUnknown 会丢掉真实采样；两者都不采用。显式版本迁移与保存原历史是本次采用的实现。

## 剩余产品目标

Gurd 完整谓词、活动 metadata/白名单/锁/事务的一致快照及真实可清候选仍未闭合，不解锁宿主清理。京东 211.1 只有 classMask=1/missingClass，历史清单仅证主程序头与未发现独立 SDWebImage framework，不能据此推断完整静态 SDK 或 writer 能力。百度/QQ/Swiftgram 私有资源事务、全 APP 增量契约、空间实际效果与数据保持、iOS 17 真机和卸载恢复仍按既定方案继续，不能以本次历史兼容替代最终目标。

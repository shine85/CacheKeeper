# 全 APP 覆盖分析与最终实施方案


## 2026-11-23 21:10 实际主体核验后的方案裁定

**当前方案不能承诺让所有 APP 总占用下降或永不增长。** iOS 的可丢弃缓存约定适用于其缓存用途；用户数据、下载和业务索引需要宿主用途及保持语义。验收改为“已支持的可丢弃缓存实际减少、后续写入按模式受控、关闭恢复、必要数据保持”，并独立列出未取得治理能力的主体，不能用小缓存成功代替整 APP 效果。

百度本机已实测到主占用不在普通图片缓存：netdisk.cachefilelist 约1.575GB，全文检索数据约215MB；image_main.image_filelist约1.384GB（不含其索引），另一个库同名表只有一个空页。image_main照片表有全局单列UNIQUE(fid)，该表总3334320行/deleted1为0的授权只读汇总完整exit0；不存在已证待删垃圾可供deleteGarbageImage处理。该入口候选停止，不继续为零候选补适配，也不调用deleteAll/truncate/VACUUM。主文件+WAL/SHM前后元数据一致，所有本轮隔离目录已核清理。数字不证明全部记录永久必要，只证明当前未发现安全淘汰这部分主体的范围。

实施分两条并行推进：

1. 完成已证通用能力的一整组修复：平台缓存read/pread与依赖语义、准确保留原因、实际writer的模式epoch与尝试/转发/阻止、关闭恢复、导出全链路、旧owner退出registry归属修正。当前21文件候选通过两轮独立源码复核；对象/C核心与编排通过，完整入口55组9PASS/46UNAVAILABLE，须同SHA云端Foundation/UIKit/RootHide打包/验deb完成后才能交付，不能标已真机修复。
2. 主体资源只接真实宿主策略。百度下一唯一有意义方向是FileDiff/ImageDiff同步owner是否已有同步范围、按需索引、保留期限或关闭可选索引的可恢复设置；尚未证明这些设置存在，不能先实现猜测开关。QQ仍需实际Documents缓存owner/同步写并发边界；抖音仍需Support主体owner；Swiftgram优先原生存储页所选媒体清理的合法高层桥接与保留条件。没有合同的主体保持未知/不可自动治理，不能硬改数据库解决容量数字。

四样本以外129个展示APP仍走统一容器发现和平台/SDK能力，不退化为四个bundle硬编码专用产品；新增/升级按能力增量复核。已有全133容量覆盖与历史SDK档案复用，不要求用户重新逐目录采集。

严格独占物理回收依然独立缺口；逻辑字节、dbstat页量、主容器减少和系统自由空间变化分别报告。不把高层完成回调、SQLite空闲页或清理计数当成物理释放证明。

本轮未发布新包、未部署产品、未执行任何APP资源清理。不能为上述诊断/证据补齐单独反复发包；整组真实验证完毕后统一交付，主体未闭合项必须明确列为未完成。


日期：2026-11-23。状态：按用户最新要求，以 Apple 官方存储语义修订实施顺序；通用缓存修复已进入开发，尚未完成构建与真机验收。

**结论：CacheKeeper 的基础功能面向全部符合条件的 APP，但近期私有资源深入分析和验收集中在四个 APP。其他 APP 的能力闭合不足；即使这四个全部完成，也不能算最终产品完成。后续以全 APP 覆盖、可复用 SDK 实现契约和资源事务为主线，沿用现有引擎集中实现、验证和交付。**

## 2026-11-23 iOS 标准复核修订（优先于下文早期任务顺序）

原方案把全部 APP 能力矩阵、私有 ABI、逐资源永久重取和独占物理证明绑定得过紧，容易继续采集而没有空间收益。修订为先修通用缓存主流程、复用宿主已有清理管理、以每项实际空间效果验收，再扩展实现族。所有 APP 仍纳入覆盖，具体能力按资源独立支持。

| iOS 资源类别 | 实际处理依据 | 必须保留的边界 |
|---|---|---|
| Library/Caches、tmp | 平台定义的可丢弃/可重建缓存；包括缓存数据库，不因格式或无关目录名拒绝，不要求逐文件证明远端永久可用 | 当前配置、目录身份、进程/在途安全、用户排除、已证明离线/草稿/唯一副本、精确 APP 保留 |
| NSURLCache、WebKit DiskCache、已验证 SDK | 复用实际 owner 的缓存 API 与队列；清存量和限写分别验证 | Cookie/登录/网站数据、内存保持、配置关闭恢复；不以替换整个 WebKit store 实现禁写 |
| Documents、Application Support、App Group、业务下载 | 这些不是统一缓存桶；优先宿主明确的缓存管理入口或资源事务 | 用户下载、离线固定、上传未同步、原件、草稿、必要数据库和索引 |
| 空间指标 | 同范围实际移除、净减少、持续使用新增、关闭恢复先形成可核效果 | 不将目录差/已分配量/卷差声称独占物理释放；物理归因另列研究，不阻塞可安全执行的缓存清理 |

源码已确认两个问题（本轮实现与审查中，未发布）：Policy 的名称子串匹配会把 authors/authentic/tokenizer 等无关缓存组件误当必要状态；Baseline 对平台缓存先读内容，Rules 又先以 readComplete 拒绝。先修平台预检依据；名称驱动的范围扩展已经撤回，既有名称边界暂保留并准确标为用途待核实。后续只按具体范围、owner、在途状态和明确排除证据迁移，不增加完整词白名单。此源码问题尚未证明是当前四 APP 总量增长的唯一原因。

挂起不是已退出的证明，60 秒只是当前项目启发式。已有逐根进程/配置采样存在批内失效窗口；需针对恢复执行/配置变更设计低成本撤销，不能每文件同步查 FrontBoard，也不能无依据地将所有自动清理改成必须强退。宿主在可用后台时间内执行的正式缓存 API 优先使用。

Swiftgram 优先核 StorageUsageScreen → engine.resources.clearStorage 及已有容量/保留时长配置，由宿主管缓存索引；停止把手工重建每种缩略图当主路线。该接口仍会删除所选本地完整媒体副本，首批不含全局 misc，必须携带必要本地资源/用户排除；宿主 completion 不证明所有 unlink 成功，也不能保证跨索引与文件删除原子性。QQ 清存量独立核清理入口，完整限写再覆盖同步/异步 writer。百度现有 deleteLocalFileTempWithCacheFileMeta 会连本地完整副本一起删，不能按方法名当临时缓存接口；已有安装资料中存在 BDPanCacheManageService 的 deleteCachedFileSpace、baseDirectory、userCacheDirectory 及容量清理入口，先解析其中对应大子树的缓存分支、参数单位、异步终态与保留集合；用户下载移除单独控制。抖音 ALog 与 Support 大缓存分别推进。

开发次序：①标准缓存误拦截与生命周期回归；②现有 NSURLCache/图片/WebKit 的同资源清理、非空写尝试、恢复实证；③已存宿主高层缓存接口与大占用；④把这些能力复用于其他 APP 并自动增量核验。能力展示同步接线，不能先重建大框架拖延真实收益。每组相关修复整体验证、统一交付；未实现的私有能力继续列缺口。

### 17:20 存储页面反馈：最终效果没有达标

用户新增截图显示百度网盘 **8.99 GB**、QQ **2.36 GB**、抖音 **2.23 GB**、Swiftgram **1.74 GB**，并反馈四者占用越来越大。截图是一个时点，不能单独计算增长速率；系统 APP 总占用与前述容器逻辑字节也不是相同口径。这个反馈说明用户要求的占用控制效果仍未达标，不能用文件删除计数抵消这一结论。

已证实的少量标准缓存删除和百度图片约 1.76 MB 的同次清理，尚未覆盖占用主体；真实限写没有闭合。原因调查必须同时区分 APP 二进制、必要持久数据、可治理缓存、派生媒体、未知资源及后台新生成，不能只修统计页面或继续增加清理频率。

最终验收新增空间效果门：同一安装身份、同一资源范围记录使用前、产生后、清理后、再次使用后、关闭恢复后的观测与动作关联。清存量要证明目标资源实际减少；限写要在真实非空尝试下证明目标新增受控；必要数据保持。整 APP 总占用作为用户可见的趋势校验，包含版本和更新时间，不能把合法新增文稿或 APP 升级导致的增长伪称清理故障，也不能用这个区别回避未受控缓存增长。

任何“已完成清理/已限制缓存”的交付结论必须同时说明**治理范围、实际空间效果、未覆盖的大占用及其后续动作**。单次 API 完成、累计删除量、静态分类或用户“没异常”均不能代替这个效果门。

基础能力是通用的，近期工作重心存在四样本偏置。更严重的是把“采集完成”和“私有资源可治理”混在同一进度描述里，导致既没有向其他 APP 扩展，也没有把困难样本的关键契约补齐。

## 3. 为什么采了几天仍有缺口

1. **静态元数据和代码窗回答的是“有何实现”，未直接回答“该活对象管理哪些资源、何时写完、哪些必须保留”。** QQ 同步支路、Swift ABI、共享消费者等没有被元数据重复扫描补齐。
2. **自然使用报告缺乏配置与实际动作的关联。** `writesBlocked=0` 没有实际尝试/放行计数，无法区分没写入、原调用放行或限制失效；用户记不得模式顺序不应成为反复补测的前提。
3. **其他 APP 的 SDK 候选没有变成逐实现兼容结论。** 61 个镜像仍主要是档案，近期没有逐族完成“复用、拒绝、重验”的产品接入与真实行为测试。
4. **旧目录队列与新容量树没有贯通。** `standardPolicyCandidates` 的 530 行和 `unknownResourceEvidence` 的 2039 行是保存观察，存在父子重叠与旧时间。不能相加作可回收量，也不能忽略最新大文稿树只继续清图片。
5. **采集退出条件偏向“收到数据”，而非“关闭一个实现决策”。** attach 超时或只得到未知跳转后继续重复，增加工具工作，却没有取得资源事务能力。

后续每次补证必须有唯一假设、目标字段、通过/拒绝标准和退出条件；失败后留下明确工程阻断，回到离线研究。相同身份、相同问题的重复无新增结果不再触发下一次完整采集。不会承诺只要多采几天，任意私有 ABI 就必然可用。

## 4. 最终设计及不变量

采用 **现有引擎 + 全 APP 能力投影 + 可复用 SDK 实现契约 + 私有资源事务**。用户已确定统一发现、按契约处理和增量核验；此处细化实现，不重新讨论逐 APP 人工白名单或全目录写锁。

不新增第二清理引擎、远程规则服务或另一份配置。文件删除依据仍归 `AxsCacheKeeperCleanupRules`；SDK/API 动作在已有 owner 模块内执行，能力投影只能读已验证结果。

每个 APP 按资源分别表示 **发现、清存量、限写、关闭恢复、必要数据保持、物理归因**，每个维度独立为未观察、检查中、支持、拒绝、失败或已验证。不得用一个 APP 总“已适配”掩盖部分资源未知，不支持限写的资源仍可有清存量能力。

SDK/私有事务的必要事实：实现族及 revision、可信来源/ABI、活 owner、资源相对范围、队列与生命周期、必要保留/引用、动作语义与结果。平台缓存直接复用 iOS 用途约定及现有安全边界；不要求逐文件 owner、原件或永久重取证明。资源 ID、原路径、对象地址和内容不出运行时内存；报告只保留固定原因、技术计数和本报告有效的匿名标记。

- 用户关闭、目录排除、必要保留优先；发现新 APP 不自动开启。
- 队列前和真正动作前重验安装、实现、owner、目录、配置与引用代际；失配只暂停相关资源能力。
- 版本用于样本和升级失效，不能凭版本字符串直接取得执行资格。已验证的相同实现族可复用，新实现先重验。
- 平台标准缓存不因 APP 升级失去通用政策；私有资源升级不能借通用规则绕过更严格边界。
- 持久化能力记录是历史证据，不是持久删除授权。重启重新绑定当前安装和活对象；未变项复用有界检查，不反复全树扫描。
- 不跟随未知链接、不整片 chmod、不调用未经确认 Swift ABI、不从接口缺失退到裸路径删除混合资源。
- API 回调、文件移除、写入受限、关闭恢复和独占物理释放分别结算。

## 6. 开发侧补证与实际行为验收

下一组同时补齐脱敏诊断：

- 写入口实际非空尝试、放行、阻止及当时配置 generation/模式；数据内容、key 不记录。
- 图片准入前后、changed/needsRefresh、恢复原因和对象生命周期；冻结首拒绝与当次失败分开。
- WebKit request/token/epoch、准备/提交/过期、后台状态和剩余时间区间；退出后 pending 不表示仍在执行。
- 每根登记命中、原始测量时间、复用/重查理由、实际 sweep 数；短调度间隔不冒称全树重扫。
- 私有事务的选中资源数、必要保留数、取消/失败、真实移除与重取结果。复杂业务 ID 只在内存关联。

这些字段随功能实现一起交付，不单发诊断包。先复用现有档案和报告；确需手机时由开发侧使用同一授权连接，按安装差异批量补最小技术缺口。只读能力探测与资源动作授权分开；不要求用户人工查目录、抓包、提供同版本 IPA 或记住过去几天的顺序。

每个启用契约必须实际验证：

1. **只清理：** 真实写入先成功，后台合格阶段清存量；必要数据可读。
2. **限制并清理：** 同等可重取负载出现非空写尝试，目标写盘受限，内存/读取和必要数据保持；无尝试记未触发。
3. **自动：** 按现有政策验证与上述两能力的组合，不改变既定模式语义。
4. **关闭：** 恢复 APP 最新原请求，真实写盘再次成功，停止新的插件动作；已有不可取消动作如实结算。
5. **三轮重开与恢复：** 可重取资源恢复，登录、草稿、离线项、原件和索引无破坏；升级、取消、并发/共享 owner 和保存失败亦覆盖。

未知或不支持的能力如实拒绝，但单靠“拒绝准确”不能声称对应私有资源目标已完成。需要把证据不足、未触发和已确认失败分开。

## 7. 独占物理回收的独立可行性门

当前 `st_blocks`、最后硬链接消失、目录差和卷可用量变化均不能证明单 APP 独占物理释放。最后链接已删除时若仍有打开文件、克隆、快照或延迟回收，也不能按逻辑字节计物理释放。

先只读核当前 iOS 16–17 / RootHide 可用的、能证明块共享与保留关系的文件系统接口。不为获得指标扩大权限、移除快照或扫描用户内容。仅在合法接口和当前设备允许可靠归因时，实现独立 PhysicalEvidence；缺条件就以明确 `notMeasured/unsupported` 结束这项研究，不继续重复采集全卷差值。

测试须含普通文件、范围外硬链接、克隆、快照保留、其他进程持有 FD、延迟回收及并发写入；无法取得真机环境的项列未执行。严格“独占物理释放”若仍不可证，该统计要求仍未满足；它独立于安全清理和可观察空间改善，不阻塞这两项的实现与验收。

## 8. 整组交付门及最终完成定义

内部按有依赖的工作包执行，**不是每个工作包发一个版本**。具体文件、接口、验证命令和检查项见 [实施计划](superpowers/plans/2026-11-23-all-app-resource-governance.md)。

开发侧完成能力投影、契约接入、相关行为测试和回归后整体审查；统一推送本组相关变更，同提交 Actions 完整原生、容量页、UIKit/真实 SDK、RootHide SDK16.5 双架构编译全部成功，再下载验 deb。云端失败先集中修关联问题，成功包才交付集中手机验收。

首次集中验收覆盖当前 18 个开启 APP 的自然使用证据及各契约代表资源；不要求手动逐个处理 133 个 APP。开发侧自动收齐状态和缺口，用户只需一次集中导出 JSON、有可见异常时说明 APP/操作。卸载与恢复是另一个明确的最终验收步骤，需要用户安排且保留配置，不自动执行。

最终关闭条件：

- 133 个当前展示 APP 全有逐资源能力及证据来源；296 登记的未操作范围、读取失败、排除、历史/未知原因完整，不能漏掉 APP 或补假零。
- 当前 18 个已开启 APP 逐项说明已支持能力；实际支持的清存量、限写、关闭恢复与数据保持有本版本证据；不支持限写不能伪称已限制，也不阻塞它的独立清存量能力；未触发项不能打勾。
- 用户反馈的占用增长得到按资源归因；同次清理净减少和持续使用新增受控有真实测量，APP 总占用趋势与必要数据增长分别解释，不能仅以删除计数通过空间效果门。
- 61 个历史 SDK 候选作为全量扩展队列逐项重验，兼容契约对多个 APP 复用；它不阻塞已证明通用修复整组交付。新装、同版本换 build、升级、容器/资源变化和重启增量流程真实通过。
- 已要求的百度下载、QQ 私有图片/文稿、抖音日志/Support、Swiftgram 媒体事务得到实现和真实恢复验收；不可用项明确列阻断，不能把“保留”算作这项资源治理完成。
- 其他开启 APP 的待识别资源按全量队列有工程结论和后续动作；核心主流程、权限/隔离、搜索、PDF、历史与性能没有回归。
- 独占物理归因按第 7 节单独关闭；iOS 16 真机、iOS 17 真机和卸载恢复分开验收。当前仅有 iOS 16.2，不能由 CI 模拟器补作 iOS 17 真机通过。

原 1123 三项及百度恢复遗漏已有开发侧实现、编译和验包；本方案接续的剩余工作是**全 APP 能力闭合、SDK 覆盖扩展、私有事务、实际限写/恢复与保持、物理可行性、iOS 17 和卸载验收**。这份分析与计划不替代这些实现和验收。


### 本轮设备证据修正

2026-11-23已实际确认百度BDPanCacheManageService → BDPanCacheDirectory → BDPanAccountServiceProtocol.userCachePath路径来源，18类方法元数据可核；技术字符串Cache/ThumbnailCache已证。限定Documents三级只读容量发现两个同名Cache候选，总分配14,632KiB，而Documents分配7,835,396KiB；说明这两个候选不是主体，不得用该服务小缓存当7.97GB已解决。目录名仍不授删除，完整作用范围/消费者和终态尚未证。所有新设备动作仅只读技术代码/元数据，没有调用资源清理、读取文稿正文或部署插件。

### 百度主占用的进一步定位（只读格式头，未读取业务记录）

最大文稿子树中18个.sqlite后缀文件合计6,465,748,992B；格式仍不能单独定用途。随后限定Documents最大的20个.sqlite，仅双读100字节格式头：最大的两个主文件为3,833,917,440B、2,630,270,976B，页大小均4096，主头空闲页分别2、0，changeCounter与validFor各自相等，WAL分别41,863,352B、290,752,552B。主文件头不代表包含WAL的当前事务快照；这些数字不能证明可回收6GB，不能直接VACUUM/checkpoint或删库。下一步是实际数据库owner、用途、保留/淘汰机制和安全维护窗口。此证据否定“只要清标准图片缓存或压缩空库就解决百度大占用”的假设。

最大的两个数据库固定技术名已由安装二进制同字面量核对为 netdisk.sqlite 与 image_main.sqlite。已有本地类名节含 BDPanDatabasesManage、BDPanDatabaseController、BDPanImageMainBaseDAO 等候选，但类名存在不证明该库的实际 owner 或可淘汰表。下一实施路线改为数据库归属与宿主维护/淘汰接口，不再以缓存目录名字增加删除规则。

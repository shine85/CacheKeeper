# 一次导出已配置 APP 的诊断

这项功能用于统一反馈目录与清理记录。采集不修改开关，不触发手动清理或清理重检；原本开启的自动清理仍按原配置工作。

## 首次反馈

1. 安装包含“诊断”入口的新测试包，按安装器提示完成重新加载。
2. 打开“设置 → 缓存管家”。先点击“搜索应用”，测试输入“百度”、`baidu`，清空后再搜索 Swiftgram；切换分类、取消搜索再输入，确认键盘和过滤都正常。
3. 点右上角“诊断”。页面显示已配置 APP 数量，包含曾保存但已关闭的配置，不受搜索或分类影响。
4. 点“补采已配置 APP”，留在此页等待队列结束。它会逐 APP 检测目录、逐可见根执行深度检测；大目录可能需要较长时间。不要同时打开其他检测页面。
5. 点“导出现有记录”，在系统分享菜单选“存储到文件”。把生成的 `CacheKeeper-diagnostics-….json` 作为附件发回当前会话，无需逐页截图。

补采中途也可点“停止补采”再导出；点导出会先停止当前补采。超时、其他请求占用、部分扫描、历史与缺失记录均可导出，不能当作完整新扫描。若“已有检测请求”一直存在，返回对应 APP 档案停止原检测，再重试。

## 报告内容和边界

- 包完整版本、系统版本、插件运行架构；APP 名称、Bundle ID、版本和当前配置。
- 每个 APP 的目录扫描、历史趋势、清理回执、网络限制及主动诊断结果。
- 深度检测的类型/年龄分布、最大普通文件和硬链接、孪生关系、保留子树样本；时间、失败、覆盖和截断状态原样保留。
- 不读取或导出通讯录、设备序列号、设备名、文件内容或原始日志；自由文本仅保留原因类别。账号段、资源标识和未知路径组件换成本次报告内一致的别名，别名表不会导出。APP 名称和已知技术目录仍可见。
- 字节数仍是各记录的逻辑统计，不等于实际可释放空间。共享硬链接可能对应同一份数据；分次记录不是原子快照。
- 系统分享由用户操作，无自动上传。应用创建的临时分享副本在分享结束后清理；你主动保存在“文件”中的报告由你保管。

## 随报告补充两句话即可

“搜索：能/不能输入和过滤；补采：完成/停止/报错。”

“问题 APP：名称；现象：退出多久后仍有什么残留，或哪项功能异常。”

百度网盘 PDF 能否离线打开、云端是否能重新下载等恢复证据仍须由用户实际操作确认，报告不能替代。Swiftgram 的主数据库与共享媒体需要分别判断，采集不会扩大其清理范围。

## 可选停止验收

开始补采后点停止，确认不再提交后续目录；导出文件中的 `collection` 应显示停止，已有记录仍存在。重新进入页面可再次导出。搜索与分享、RootHide 请求通信属于真机验收项，Theos 编译不能替代。

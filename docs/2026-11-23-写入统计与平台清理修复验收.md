## 本轮改动

- 标准缓存按平台用途进入既有清理预检，不再被无关内容读取失败阻断；身份、年龄、链接、取消、用户排除与已知保留规则继续生效。精确 APP 规则可处理其已授权依赖集合，平台 fallback 不取得这些依赖的删除权限。
- 图片 SDK 的两条实际 writer 分别记录有效输入的尝试、原调用放行和阻止；按配置、安装与模式代际保存最多 16 组。旧 owner 被移除后，其仍存活的 disk 写入不再归入旧代际。放行只证明转发原调用，不证明实际落盘。
- 同一份严格验证的写入回执同时进入规范图片记录、能力摘要与全 APP 清单；旧回执不补造零计数，非法字段不传播。
- 名称匹配引起的保留显示为“用途未核实”。没有发布按完整词匹配扩大删除范围的方案。

## Actions #199 暴露的问题与修正

提交 `2b450ec6a2a584bee2e46ffdc6bdeddce3132924`，运行 `45187795743`：真实原生 **50 PASS / 5 FAIL / 0 UNAVAILABLE**。后续 UIKit、容量页面、Theos 与发布均未执行，没有 199.1 包。

1. `storage-inventory`、`image-runtime-source`、`image-write-observation`、`image-main-view` 都在新增回执校验链路失败。根因是 Objective-C 文件中 `@(droppedEpochs > 0)` 产生整数 NSNumber，而消费者要求真正的 CFBoolean。生产端改为显式 BOOL 装箱；消费者继续拒绝数字 0/1 冒充布尔值。
2. `observation-export` 新增断言需要全 APP 清单中存在测试 APP，但夹具没有登记或保存配置来源。补写明确禁用的 APP 配置与空目录选择，并验证导出前后文件不变；不改变生产清单的集合来源或开启状态。
3. 新增真实 Foundation 回归，覆盖实际生产记录、空记录、写入、16 代际上限淘汰、溢出、完整回执及 XML／二进制 plist／JSON 往返；固定 #199 生产头必须精确失败，当前头必须通过。原固定旧 writer 反例和实际 writer 行为测试仍保留。
4. 按实际新增子进程上限调整该组预算，并在编排测试中核对；单个编译和行为命令仍有独立期限。

本机已经执行 ARM64／iOS 16.5 对象编译与 Python 编排；对象编译不代替 Foundation 行为。Windows 缺少 Foundation/UIKit 执行环境，完整行为必须由后续同提交 macOS 作业验证。

## 私有主体核查的收敛结果

- 百度 `image_filelist` 授权汇总完整返回总 3,334,320 条、`deleted=1` 为 0。停止无收益的垃圾记录清理路线；尚未证明可安全淘汰主体索引的宿主策略。不清整库、不自行删除有效索引。
- 抖音 41.2.0 当前最大 Support 子树的名称与安装程序完整技术字面量 `gurd_cache` 匹配；只读匿名类型统计显示前三大分支主要为网页代码和图片。该结果关闭此前 YYCache 目录猜测，后续核 Gurd 自身缓存管理、活跃资源与更新事务；目录名或扩展名仍不授删除权限。
- 抖音随后已完成真实类表、class／meta／RO、276 个方法、直接转发与过期策略代码核验。`IESGurdKit` 将过期清理交给 `IESGurdExpiredCacheManager`；过期参数按天，时间戳为毫秒，未记录最近访问的资源不进入该过期判定；只有宿主目标分组或通道命中的资源才比较年龄。同 accessKey 300 秒内有直接回调路径，因此回调不等于实际删除。普通白名单清理走 `IESGurdFileBusinessManager`，尚未证明与过期路径保留规则一致。不能据这些入口直接开放主体自动清理；下一实现必须核宿主目标范围、白名单保持、实际删除终态和关闭恢复，不更改全局过期开关或伪造目标列表。
- Swiftgram 13.0/build319 的 `StorageUsageScreen` 自身 3 条 Objective-C 方法经真实方法表、两页 format 6 链及选择子字节确认，仅为 `initWithCoder:`、`viewDidLoad`、`.cxx_destruct`。关闭该类直接 Objective-C 清理入口路线；不从这些方法臆造 Swift 清理 ABI。宿主 Swift 存储管理与必要本地媒体保持仍待接入。
- QQ 文稿主体仍缺可执行的资源 owner 与保留／恢复事务；已有图片接口证据不授权清理整个 Documents。

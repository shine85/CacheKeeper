# 217.1 采集报告复核与一次性采集方案

复核日期：2026-11-27。依据目录内三份完整 JSON 原件及其 SHA-256、当前采集脚本和已完成的 WQManager 固定提交源码复核。后续“本轮实现”部分记录离线报告链路增量；没有连接手机或发起新采集。

## 报告能证明什么

三份导出分别为“限制并清理”“只清理”“关闭”，每份包含 139 个 APP，导出模式均为 `savedRecords`，`collection.rescanned=false`。因此它们保存了报告生成时的已有记录，不是重新扫描 139 个容器。容量测量均为 `partial / savedObservationUnverified / notRevalidatedAtExport`，不能用来宣称本轮重测全容器容量。APP 扫描时间以及各 APP 的 `hostObserved` 仍指向旧记录；百度图片 SDK 是少量具有本轮新 event/epoch 的子系统。

| 阶段 | 百度图片 SDK 的新证据 | 可以下的结论 | 不能下的结论 |
|---|---|---|---|
| 限制并清理 | SDK discovery `classMask=15`、installation verified；epoch 2 `prevent` 下非空写入 30 次、blocked 29、allowed 1；同进程新 action `apiCompleted`，SDK 平目录从 1 个文件/1966 logical bytes 到 0 | 百度已观测到非空写入；绑定 writer 的限制钩子挡住 29 次 | 不能声称所有百度写入路径都受控；允许的 1 次需结合逐次原调用结果才可归类；`physicalRelease=notMeasured`，没有物理释放量证据 |
| 只清理 | epoch 2 `clean` 下非空写入 31 次、blocked 0、allowed 31；同进程新 action 将 23 文件/790605 logical bytes 降到 0 | 只清理模式下该绑定 writer 有阳性放行对照；图片 SDK 子目录清理前后计数完整 | 不代表百度 Documents 主体已证明为缓存；逻辑 bytes 不等于独占物理释放；不能覆盖其他未绑定 writer |
| 关闭 | 新事件 reason 为 `appDisabled`；所有 writer epoch 的非空 attempts=0，identity 为 `notRevalidated` | 关闭路径产生了禁用状态事件 | 没有非空写入尝试，不能证明写入恢复；应标为“关闭恢复未验证/本阶段未触发” |

清理历史需按 `packageVersion`、`mode`、`coverageComplete` 和 round 分开解释。部分轮次 `coverageComplete=false`；历史还混有 216.1 记录。不能把汇总 `cleanup.bytes/removed` 当成本轮私有 SDK 主体效果。百度三份报告的 SDK action 可作为独立小范围效果证据，不可泛化为其 Documents 主体。

另四个目标：抖音 Gurd 为 `scopeUnproven`，没有提交；QQ、京东图片 SDK 为 `unsupportedSDK`/缺类，非空 writer attempts 为零；Swiftgram 标识是 `app.swiftgram.ios`，不能用旧 bundle 猜测，当前图片 SDK 同样没有可用的已适配写入证据。这三份报告没有解决这些私有资源契约。

## 根因与工具缺口

当前 `scripts/collect_device.py --prepare-session` 是离线报告打包，输出 `executionAvailable=false`。`device_collection_batch.py` 的 `RUNTIME_ADAPTERS` 只有 APP 到名字的映射；`foregroundQueue` 没有逐 APP 运行时执行器。因此目前没有可交付的手机端“一键采集工具”。报告显示的重复读取也暴露出采集设计缺少阶段任务与报告原子关联：保存导出覆盖了完整历史快照，却未证明该轮对每个 APP 做了新测量。

运行时证据必须遵循已存在的安全边界。此前的私有运行时取证请求被自动审核终止，不能通过换 SSH/代理/插件 hook/其他通道执行同一被拒动作。实现侧应先检查现有获准的 Preferences/HostEvidence/DiagnosticChannel 契约；若某字段没有获准且能实际运行的合法采集入口，就在预检和最终报告标记 `blockedByCapability`，不伪造模块、不读应用内容，也不让用户重连后碰运气。

## 推荐的一次性工具方案

推荐在现有 CacheKeeper 工程内扩展一个**签名的手机端采集向导**，配套桌面侧只负责部署、接收与验包。它不是另建越狱 shell 工具，也不是用 SSH 替代宿主契约。每个 APP 使用明确的 `CollectorModule` 实现和版本化输入/输出 schema；运行前做能力预检，所有必需模块不可执行时不得显示“整批就绪”。

一次会话覆盖多个必要阶段，而不是声称一次快照能证明所有行为：

1. 创建不可变 session ID；绑定 APP bundle、安装 generation、插件/APP 版本、模块版本、配置 generation、阶段、事件/epoch 和证据对象 SHA。
2. 开始前读取已有静态身份/容量基线；只刷新确实陈旧或阶段验收要求更新的字段，不重新扫完整 139 APP 清单。
3. 依次呈现正常负载、非空写入对照、受支持且已证明范围的清理、关闭恢复等阶段；只要求用户在各 APP 做预先定义的最少动作。没发生写入就记 `notTriggered`，不得当通过。
4. 每阶段立即落盘为 append-only 事件，断线恢复仅调度显式未完成项；已成功项不重采，旧值不覆盖新 session。跨阶段保留安装身份和事件因果链。
5. 结束时自动执行完整性门控：逐 APP 检查模块是否实际执行、身份是否匹配、事件是否新鲜、样本是否 complete/partial、阳性对照是否触发、错误阶段与错误码、文件哈希和必需验收字段。按 `passed / failed / notTriggered / insufficientEvidence / blockedByCapability` 输出。
6. 手机端生成一个脱敏 JSON/ZIP 报告及 manifest/SHA；保留原始分阶段记录供开发侧复核，不包含消息、缓存内容、完整私有路径或凭据。电脑断线不丢手机已完成的阶段，恢复连接后只收回未同步对象。

五 APP 模块职责：抖音 Gurd 先证明真实清理范围与保留谓词、同源候选快照、有限候选采样和提交前一致性；范围未证明时只报告缺口并禁止提交。QQ、百度主体、京东、Swiftgram 各自建立 owner→队列→资源类别→必要数据保护契约；百度现有图片 SDK 单独保留，不能冒充 Documents 适配。所有限制模式必须统计每种已绑定 writer 的非空 attempts/blocked/allowed，并在 clean 与 disabled 阶段做同一安装身份下的对照。任何未获契约支持的资源只测量，不清理。

## WQManager 的引入边界

已复核上游固定提交 `42d65b4142fdf8884f04c6623575b2d944589c86`。引入的是设计原则，不复制代码：容器身份复核、阶段化测量与 `interrupted` 状态、按占用给出补证优先级、每次操作明确状态。CacheKeeper 已有 FD-relative cursor、身份和 SHA 父链，应复用而不是再造扫描器。其 `Library/Caches`/`tmp` 白名单、目录大文件排名与逻辑 `freed` 不能扩张成五 APP 私有缓存规则或物理释放声明。上游 GPL-3.0-or-later；当前仅参考且未复制实现，不需引入其代码。

| E. 一次手机集中采集 | 一次安装/打开向导/按屏幕指引完成五 APP 阶段/手机生成报告；电脑只收取同一报告包 | 五 APP 每阶段逐项有结果；百度 disabled 恢复必须有非空 attempts；抖音 Gurd 连续两个 operation 均 submitted 且 before/after complete；其余 APP 有契约覆盖及必要数据保持证据 |

所谓“一次性”指一次部署、一个会话、统一阶段引导、断点不重采和单一报告包；并不承诺一次用户动作能触发每个 APP 的磁盘 writer。工具必须能提前提示缺失触发条件，并在阶段结果里准确标记未触发。

### 2026-11-27 会话诊断来源覆盖门控

手机端集中会话的 diagnostics phase 之前只用 `apps != nil` 作为 complete 条件，这会把安装数组存在但配置/选择/快照、系统注册表清单或容器范围采样不完整的结果记成完整。现改为检查报告 `sourceStates`、安装枚举、`containerCoverage`、`storageInventory.registry`、`scopeObservation` 及每条安装记录的元数据可用性和 verified 身份；任一缺口时持久化 `partial` 与 `missingSources`，不生成身份哈希或配置 generation。10项生命周期源码回归与31项会话/阶段/离线打包测试通过，py_compile、目标 diff-check 通过；Foundation 原生 runner 在 Windows 因缺 macOS/xcrun 返回 UNAVAILABLE/2，UIKit/Theos/真机未验证。仍缺手机端私有 APP 执行模块、真实身份/配置 generation绑定，以及终端原生与设备验收。

### 2026-11-27 宿主自报告与集中会话关联

向导宿主阶段现在持久化本轮起始时间、各 APP 自报告时间、多个 responder 标志与 `transportTrust=unauthenticated`；旧时间、多 responder、保存失败或未观察的行使阶段降级为 partial。集中会话完整性门再次校验逐 APP 时间与信任元数据，拒绝调用侧错误标 complete。未改变 notify 协议、未把自报告提升为执行证明。新增源码回归 RED→GREEN；31项离线回归+新增源码用例、py_compile/diff-check 待最终实跑，Foundation/UI/Theos/真机仍受环境限制未验证。

### 2026-11-27 中断宿主阶段显式续作

另修复宿主预检 interrupted/cancelled 后无法在同会话续作的问题：再次点击开始时先持久化 retryScheduled，再开始新轮请求；complete/partial 阶段仍不可重复执行。该轮次关联门控要求响应秒级时间戳不早于向导开始秒，且单一 responder；超时、多 responder、保存失败均保留证据并降级 partial。

最终本机复核：11 项集中会话生命周期源码回归及阶段归一化/离线打包回归共 33 项通过；涉及 Python 文件 `py_compile` 退出 0；目标 diff-check 退出 0。Foundation session runner 明确返回 `UNAVAILABLE/2`（Windows 无 macOS `xcrun`），未运行原生测试；UIKit/XcodeGen/Theos、云端构建、真机和五 APP 行为仍未验证。宿主阶段结果仍为未认证自报告，不代表 APP 侧清理或写入控制已生效。

### 2026-11-27 会话实际阻断与核心契约复核

真实 iOS 16.5 SDK 编译先复现了 `beginPhase:` 同作用域重复声明 `phases`；继续编译页面发现缺少宿主目标函数头文件。另从实际调用链确认：新会话嵌套 literals 不可变、copy setter 使保存失败回滚后的字典不可变、能力阻断过滤令全部实际向导会话不可恢复、容量 retry 没有进入 running、后台记录缺服务必填字段、内存 JSON 被过早标成已导出。

本轮集中修复上述问题：会话使用深可变内部状态和独立证据快照；中断需要显式 retry，终态不重放；容量 clientLifecycle 中断只记录实际 epoch/观测时间，不伪造服务结束与计数；同一页容量按钮随阶段更新；放弃等待先记客户端中断，终态保存失败保留原结果并显式重试保存，不重测。诊断开始前持久化 running，完整脱敏 JSON、SHA-256、诊断和 export 终态在同一个 plist 原子保存。写失败回滚状态，页面只重试保存原结果；重开校验 SHA 与完整 session 投影并复用同一字节报告。已保存失败报告也可再次找到。普通诊断仍沿用原有内存/分享行为。

该轮结束时容量完整 payload 尚未逐阶段保存（已由下方耐久源续作补齐）：若 A 容量终态后退出、B 覆盖全局结果，重开 A 的导出会校验 A 的 epoch、finishedAt 和三项根计数；不匹配时不借用 B 的数据，容量标记未取得，诊断为 partial，缺口为 `capacitySessionEvidence`。这防止串会话，但尚未满足“每阶段完整证据立即落盘”的全部要求。

# 集中采集目标纠偏与实施缺口

2026-11-26。本文新增，无旧版本可备份。依据当前产品源码、已保存的技术证据和本轮两项独立只读审计；不是已实现功能或新的手机操作通知。

## 目标与工作顺序纠正

用户要的是：开发侧先把工具完善并验证，再一次部署到手机、集中操作、统一回收足以支持剩余适配的证据，避免反复 SSH、重复采样和拆小包。216.1 的五宿主预检只补了加载版本、配置可读性和发布状态，不满足这个目标。它通过测试不等于完整采集工具通过验收。

不再要求用户先做 216.1 五项预检才能继续开发；不将旧综合报告生成时间当作本轮组件实测时间；不重复已完成的全机身份/19 个独立 SDK 候选检查。已有断点批次和容量基线继续复用。用户若自行提交新的预检结果仍可分析，但它不能代替资源候选、保留规则、写入和恢复证据。

## 为什么此前没有解决

这里有三种不同原因，不能统一写成“还缺真机证据”。

1. **生产功能没实现。** Gurd Source 始终构造 `scopeUnproven`，Engine 仅在测试宏下接受测试正向范围；采样仍遍历全根。没有真正的生产候选来源与消费链，重复运行 APP 不会自动补出它。
2. **工具没有对应执行能力。** `--prepare-session` 仅输出三份文档；`RUNTIME_ADAPTERS` 只是标签，foregroundQueue 没有消费器。现有 runtime JS 只看镜像和方法身份，不提供五 APP 的 owner、资源用途或一致性窗口。216.1 HostEvidence 同样不提供这些信息。
3. **有独立的执行阻塞。** 两段广泛私有取证任务曾在 2026-11-26 02:21:09Z 和 02:21:12Z 被自动审核终止，错误为 `Potentially unintended activity` / `misalignment_policy_violation`，没有指出具体触发命令，当前工具没有提供该拦截的恢复入口。这不等于所有本地分析都被禁止，也不允许换工具、代理、插件内 hook 或内存读取来继续被拒任务。

本轮只做源码和已有本地技术证据分析。没有连接手机、生成新设备任务、执行清理或修改权限。

Gurd 较早技术摘要中的“metadata owner/路径未知”“锁 getter 未知”“进程未运行”已被后续材料补齐或纠正。以 `packages/采集报告/2026-11-25-final-followthrough/gurd-scope-progress.md` 与 `gurd-real-scope-proposal.md` 为较新依据，不按旧摘要重复取证。

“相关 writer 一致性”指影响候选/保留判定的变更，并非证明整个 APP 的全部写入。经证明的合法串行队列、不可变发布或覆盖相关变化的真实代次可满足条件，不强求一把全局锁。两次摘要相同只证明两次观察相同，不能证明中间没有变化。

## Gurd 必须成组接通的代码

- `AxsCacheKeeperGurdSource.m`：真实 Source 负责取得并认可候选快照；不能由导出报告字典、测试 fixture 或用户目录选择生成授权。`prepare`、`validate`、`submit` 需使用同一来源和一致性条件，不能继续全字典比较含动态 proof 的 binding。
- `AxsCacheKeeperGurdCache.m`：before/after 固定同一候选集合，复用现有 FD-relative cursor 分片，不扫描保留兄弟目录。合计预算和 inode 去重跨候选共享，祖先链每片重验；已完整观察且已提交的候选叶被删除可在父链不变时计零，其他访问失败、换根、重建或链接仍为 partial。
- 保留现有用户范围、排除项、安装身份、撤销和后台生命周期检查。完整采样不等于删除授权；void 宿主调用返回不等于完成；不把测试正向范围升级成真实宿主适配。

这些内容仍是待实现，不能以独立采样器 fixture 通过交付“Gurd 已修复”。没有真实候选来源时，孤立增加采样器不是当前完整工具的交付。

## 集中工具的最小完整形态

沿用现有身份/容器发现、认证传输、对象哈希与断点链，只有以下各项都落到实际代码及真实开发侧验证后，才安排手机集中操作：

1. **可执行分发。** 每个 APP 有实际模块与固定输入/输出，启动前能判断模块存在和所需证据范围；不能只有 adapter 字符串、pending 队列或 README。未实现模块必须阻止“整批就绪”。
2. **耐久会话关联。** 一个会话关联 APP、安装身份、阶段、请求/事件/epoch、原始回执哈希与保存结果。断线续未完成项，成功项不重采。现有 HostEvidence 请求仅在 RAM 中关联，原文件被覆盖后不能严格证明同批次；不能补一个时间戳就声称关联完成。
3. **具体资源证据。** 按上表提供最小匿名技术字段；不读用户内容或把大目录直接分类为可删。初始化未知、对象无有效生命周期、同步无法证明时输出准确失败阶段，不能返回空候选成功。
4. **阶段化验证。** 一次部署可包含正常负载、非空写入、受控清理前后与关闭恢复多个阶段；一次只读快照不可能证明这四件事。未经证明的资源不执行清理，不以调用完成或计数归零代替效果。
5. **结束前自动核查。** 逐 APP/逐阶段检查所需字段、身份、来源、是否新事件、完整性与错误。区分工具未实现、执行失败、未触发、证据不足和可进入修复；统一回收原始证据与摘要，不把压缩包生成成功当作资源契约完成。

现有 `scripts/device_collection_diagnostics.py` 只分析 scan/image/gurd/cleanup，尚未纳入 hostAutomatic/hostObserved；这是回收链缺口，不能把修这个字段遗漏当作私有模块完成。

## 当前结论与后续边界

完整手机采集工具和五 APP 私有适配尚未交付，本轮没有新包。先消化现有技术字节，得到可复核的新结论；剩余模块必须有合法、可执行的真实证据路径，才能继续实现和验收。当前被拒的私有取证没有恢复入口，不承诺下午可一次采齐，也不要求用户为不可执行模块提前重连。

只有范围/保留与写入契约取得真实证据、整组实现和测试完成，才统一编译验包并安排一次集中手机操作。目标手机结果仍可能暴露新问题，不能承诺一轮采样必然证明所有未来状态；能承诺的交付条件是避免已知缺模块、重复采已有内容和用辅助成果冒充核心完成。
